# ToDo: ローカル LLM の処理速度改善 (KV キャッシュの再利用を守る・生成量を減らす)

> 作成日: 2026-10-25 / ステータス: **未着手** (計画のみ。 改修は今後実施)
> 前提: [prompt-prefix-stability.md](prompt-prefix-stability.md) (状態通知の追記化、 2026-10-25 実装済) の続き。
> 関連: [response-latency-improvement.md](response-latency-improvement.md) / [prompt-cache-cost-reduction.md](prompt-cache-cost-reduction.md)

## 背景
- myppt セッション (2026-10-24) で 1 回の LLM 呼び出しが 17〜44 分。 主因 (日時・Goal・ToDo を履歴より前に置いていた) は
  `1dce520` で直したが、 実機での効果は未確認。
- llama.cpp + ハイブリッドモデル (Qwen3.5 以降) は、 プロンプトの途中が 1 か所でも前回と食い違うと
  保存済みチェックポイントにしか戻れず、 実質 0 から全部を再計算する。 通常の Transformer より「途中の書き換え」 の損失が大きい。
- 調査 (2026-10-25、 コード読みによる。 実機ログでは未確認) で、 主因以外にもキャッシュを壊し得る箇所が見つかった (下記 T2〜T4)。

## 方針 (設計思想)
- **測ってから直す**: どの破壊が実際に何回・何トークン分起きているかをログで確認し、 効果の大きい順に直す (T1 を先に行う)
- **メインの文脈のキャッシュを最優先で守る**: 補助処理 (判定・評価・圧縮・忘却) がメインのキャッシュを追い出さないようにする
- **環境を知っているときだけ踏み込む**: サーバのスロット・キャッシュ容量に依存する最適化は、 利用者が「独占利用」 と宣言した
  ローカル環境に限る。 共有サーバ・クラウドでは今の動作を変えない
- **品質を落とす最適化は条件を明示する**: 思考の無効化などは、 どの場面で無効にしてよいかを根拠 (計測) とともに決める
- 前方一致の不変条件 (CLAUDE.md「プロンプトの前方一致を壊さない」) は緩めない。 例外を増やす場合は理由の申告 (`prefix_break`) に乗せる

## ToDo

- [ ] `npm run analyze:loop` に「キャッシュ率の推移」 と「キャッシュが落ちた呼び出しの直前に起きたこと」

- [ ] 結果を本書に表で残し、 T2〜T4 の優先順位を確定する

### T2. 補助 LLM 呼び出しがメインのキャッシュを追い出さないようにする (効果 大の見込み)
現状: 次の処理がメインと同じ provider・同じモデルで、 内容の違う短いプロンプトを送っている。
`--parallel 1` の llama-server では同じスロットの KV が上書きされ、 次のメイン呼び出しが全部の再計算になる可能性が高い。

| 呼び出し元 | 箇所 | 頻度 |
|---|---|---|
| 意図判定 / 完了判定 | `src/agent/intent-classifier.ts` (ヒューリスティックで決まらない時) | 応答完了ごと |
| 進捗判定 (Q→A gate) | `src/agent/agent-loop.ts` の `judgeProgress` 呼び出し | standard 以上で応答完了ごと (最大 3 回) |
| evaluator (second LLM 無し時) | `src/agent/evaluator.ts` | 条件付き |
| 圧縮 / 忘却の要約 | `hierarchical-compressor.ts` / `compress-text.ts` / `forgetting.ts` | 文脈が溢れた時 |
| handoff / goal 昇格 | `handoff.ts` / `goal-promotion.ts` | まれ |

- [ ] 補助呼び出しの経路を 1 か所 (例: 補助用 provider の取得関数) にまとめ、 振り分けを差し替えられるようにする
- [ ] 振り分け先の選択肢を比較して決める
  - a. 別サーバ・小さいモデルへ振る (既存の second LLM 設定を流用できるか確認)
  - b. 同じサーバの別スロットに固定する (llama.cpp の `id_slot`。 `--parallel 2` 以上が前提。 chat エンドポイントで効くかを版ごとに確認)
  - c. サーバの `--cache-ram` (ホストメモリへのプロンプト退避) に任せる (既定値・ハイブリッドモデルで戻せるかは版により異なるので確認)
- [ ] 補助呼び出しの前後でメインのキャッシュ率が落ちないことを T1 の計測で確認する

### T3. 独占利用のローカル環境では、 サーバのキャッシュ構成をアプリが把握して使う
考え方: 1 人で独占利用するサーバなら、 スロット数・スロットあたりの文脈長・キャッシュ容量を
アプリが前提にしてよい。 把握していれば、 補助呼び出しのスロット割り当てや、 圧縮・忘却を始める位置をより適切に決められる。

- [ ] 設定項目を設計する (例: `localServer.exclusive: true` と、 スロット数・`--cache-ram` 容量・チェックポイント数)
  - 取得できる値はサーバから読む (`/props` の `n_ctx` / `total_slots` は `src/providers/llamacpp.ts` で既に読んでいる。 `/slots` の利用も検討)
  - 読めない値 (`--cache-ram` 容量など) だけ利用者が設定する
- [ ] 把握した構成を使う場面を決める
  - メイン用・補助用のスロット割り当て (T2-b)
  - 補助呼び出しの前にメインのスロットを保存し後で戻す (`/slots/{id}?action=save|restore`、 `--slot-save-path` が前提) かの判断
  - キャッシュに載り切る文脈長を基準に、 圧縮・忘却の開始位置を決める
- [ ] `exclusive` でない場合 (共有サーバ・クラウド) は現状の動作から変えないことをテストで保証する
- [ ] 注意: llama-server の `-c` × `--parallel` は合意済みの設定を維持する (dev-workflow スキルの規約)。 アプリはサーバ設定を勝手に変えない

### T4. 依頼の区切りでの書き換えを減らす (効果 中〜大の見込み)
- [ ] span 終了時の揮発メッセージ除去 (`purgeEphemeralAtSpanEnd`) は履歴の途中を消すため、 ハイブリッドモデルでは依頼ごとに全部の再計算になる。
      消さずに残す / 末尾に「無効化」 のノートを足す方式と、 文脈が増えることのトレードオフを比較して決める
- [ ] 忘却・圧縮のノート (履歴途中の system) は `openai-compat.ts` の `mergeSystemMessages` で先頭の system に結合され、
      system 直後から全部が再計算になる。 その位置に user ロールで置く案を検討する (通常の Transformer ならノートより前を再利用できる)。
      `prefix_break` では見えない変換なので、 T1 で頻度を見てから判断する

仕組み (`ChatParams.disableThinking` → `chat_template_kwargs.enable_thinking=false`) は既にあり、 補助呼び出しでは使っている。

- [ ] メインの呼び出しで思考を無効にしてよい場面の候補を洗い出す

- [ ] 思考を無効にすると、 思考の有無で描画が変わるテンプレートでは前方一致が崩れないか確認する (T1 の計測で確認)
