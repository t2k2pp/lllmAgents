# 実行環境情報の補強と「データを扱うアプリの土台」 の読み取り

2026-10-14 作成。 マインドマップ作成セッション (`~/.localllm/logs/sessions/2026-10-14T09-12-23_main.jsonl`,
作業フォルダ `C:\Users\osia3\GitProjects\mindmap`, モデル Qwen3.8 Flash Next) のログ分析から設計。

## 1. 観察されたこと

| ターン | 起きたこと | 直接の原因 |
|---|---|---|
| t3〜t4 | bash で `/tmp/mm.js` を作り、 heredoc で書いた node スクリプトの中で `readFileSync('/tmp/mm.js')` → `ENOENT: c:\tmp\mm.js` | git bash の `/tmp` は `%TEMP%` に割り当てられるが、 ネイティブの node はスクリプト内の文字列 `/tmp/...` を `C:\tmp\...` と解釈する |
| t9 | `python - <<'EOF'` でテストを書き換えようとして失敗 (`Python was not found; ... Microsoft Store`) | `python` は Microsoft Store の「アプリ実行エイリアス」 (偽物) で、 実体の Python は入っていない。 `which python` では見つかってしまう |
| t11 | `sed` の置換が関数宣言まで書き換えて構文を壊す | 不注意 (環境とは無関係)。 自力で回復済み |
| t17 | ユーザー「空の状態にするには?」 → 「空にする」 ボタン追加・初回をブランクに変更 | 初回起動が `localStorage || sampleTree()` で、 新規作成の手段が無かった |

環境情報 (system prompt の `# Environment`) には `Platform: win32` と `Shell: git bash (use Unix syntax ...)` が
入っており、 **OS とシェルは伝わっていた**。 不足していたのは次の 2 点:

1. **git bash 上でネイティブの Windows プログラムを使うときのパスの扱い**。 git bash はコマンドライン引数の
   `/c/...` `/tmp/...` を自動変換するが、 スクリプトのコードやファイルの中に書いたパスは変換しない。
2. **実際に使えるインタプリタ**。 モデルは Python がある前提で手を動かし、 失敗してから知った。

「新規の状態が無い」 件は、 冒頭の「含める」 宣言で「よくある機能」 (ズーム・Undo・エクスポート等) は
挙げたのに、 **道具としての土台 (空から始める・新規・保存・開く)** を観点として持っていなかったのが原因。
洗い出しガイド (`requestScope`) の観点が「作品らしさ」 (ゲーム寄り) しか無かった。

## 2. 対策

### 2.1 環境情報 (src/agent/system-prompt.ts, src/agent/runtime-tools.ts)

- `Python:` 行を追加。 `python3` / `python` / (Windows のみ) `py` を **実際に `--version` で起動して**
  確かめる。 Store のエイリアスは起動すると失敗するので「無い」 と正しく判定できる。
  - 見つからなければ `not installed — use node for helper scripts` と出す
  - 判定はプロセス内で 1 回だけ (キャッシュ)。 session 内で安定な値なのでプロンプトキャッシュを壊さない
- Windows のみ `Paths:` 行を追加: 引数のパスは git bash が変換するが、 スクリプト内に書いたパスは変換されず、
  node/python からは `/tmp/x` が `C:\tmp\x` になる。 スクリプト内では `C:/Users/...` 形式を使い、
  一時ファイルは作業フォルダの下に置く。

`# Environment` は常駐部分の上限 (tests/agent/request-scope.test.ts の 7,900 字) の **後ろ** にあるため、
上限には影響しない。

### 2.2 データを扱うアプリの土台 (src/agent/shared-principles.ts, src/agent/tool-guides.ts)

- 常駐の `# Reading the request` (T1/T2/T3) に 1 行: ユーザー自身のデータを作る・編集するアプリでは、
  空から始める・新規・保存・開くは「追加機能」 ではなく土台。 見本データは選んで読み込む形にする。
  - 冒頭の「含める / 外す」 宣言はガイド注入 (todo_append の結果) より前に書かれるため、 常駐に置く必要がある
- 洗い出しガイド `requestScope` に「道具・アプリ」 の観点を追加 (始め方 / 新規・保存・開く・消す /
  作ったものが失われない / その種類の定番機能)。 既存の「作品らしさ」 の観点はそのまま残す。

特定アプリ (マインドマップ) 向けの記述はしない。 一般原則として書く (対症療法禁止の方針)。

## 3. やらないこと

- python 以外のツール (jq, make 等) の列挙: 失敗例が無く、 常に出すと冗長。 必要になったら追加する
- `/tmp` を自動で書き換える: スクリプトの中身を書き換えるのは推測が過ぎる。 情報を渡してモデルに任せる
- sed の誤置換対策: 環境情報の不足ではなく、 既存の「同じ失敗を繰り返さない」 原則と自力回復で足りている
