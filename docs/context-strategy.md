# コンテキスト戦略 設計書 (区切りでの圧縮・忘却・Clear の使い分け)

> **ステータス**: 2026-08-13 設計 / 実装済み (未実機検証)
> **前提**: `docs/context-forgetting.md` (F2: 忘却機能) が実装済みであること
> **関連**: `docs/context-intelligence.md` / `docs/ephemeral-context-design.md`

---

## 1. 背景

### 1.1 現状: 発火条件が 1 つしかない

コンテキスト操作が起きるのは **「推定トークンが閾値を超えたとき」** だけである。

```
if (tokens > contextWindow * threshold) { reduce() }
```

これは **作業の最中に突然走る**。 モデルがファイルを 3 つ読んで編集に入ろうとした
まさにその瞬間に、 数十秒かけて履歴が要約される。 悪いタイミングで、 悪い状態
(作業途中で捨てられないものが多い) で発火する構造になっている。

### 1.2 人間の作業の区切り

実際の作業には **自然な区切り**がある。

- ToDo を 1 つ完了して次に移るとき
- `git commit` を打ったとき
- ユーザーが「次はこれをやって」 と話題を変えたとき
- 計画フェーズを終えて実装に入るとき

**区切りでは捨てられるものが圧倒的に多い**。 直前のタスクの探索過程・試行錯誤・
読んだファイルの中身は、 次のタスクにはほぼ要らない。 逆に作業の最中には
何ひとつ捨てられない。

同じ「削る」 でも、 **いつやるかで削れる量と失うものが桁違いに変わる**。

### 1.3 やりたいこと

1. **区切りを検出**して、 そこでコンテキストを整理する
2. 区切りの強さと使用量に応じて **手段を使い分ける** (忘却 / 圧縮 / Clear)
3. **山場の前に先回りして**枠を空けておく (作業中に発火させない)

## 2. 5 つのアクション

| アクション | LLM 呼び出し | 削減量 | 失うもの |
|-----------|-------------|--------|---------|
| `none` | — | 0 | — |
| `forget-thinking` | **不要** | 中 | 探索の過程 (読んだ中身)。 **メインストーリは無劣化で残る** |
| `forget` | 1 回 | 大 | モデルが選んだもの (F2) |
| `compress` | 4〜5 回 | 大 | 全体が要約により劣化 |
| `clear` | 1 回 | **最大** | 履歴そのもの。 引き継ぎメモだけが残る |

### 2.1 `forget-thinking` — メインストーリだけ残す

**LLM を呼ばない決定論的な忘却**。 ユーザー要望の
「区切りが過ぎた時に思考を忘却しメインストーリのみ残す」 に対応する。

区切りより前のセグメントに対して、 機械的に以下を適用する:

| セグメント | 扱い |
|-----------|------|
| `user` | **全て残す** (無劣化) |
| `assistant_text` | **全て残す** (無劣化) |
| `tool_batch` (読取系のみ: `file_read` / `grep` / `glob` / `web_fetch` / `web_search`) | **thin** — 呼び出し記録は残し結果本文を落とす |
| `tool_batch` (書込・実行を含む: `file_write` / `file_edit` / `bash` / `task` 等) | **残す** — 何をどう変えたかは作業の本筋 |
| `assistant.thinking` | 削除 |

「探索は捨てる、 やったことと言ったことは残す」 という 1 本のルール。

これが強力なのは **LLM 呼び出しがゼロ**な点である。 待ち時間ほぼゼロで、
実測上コンテキストの最大の占有源 (読取系ツールの結果本文) が消える。
区切りのたびに気軽に走らせられるので、 **そもそも閾値に到達しなくなる**。

読取系と書込系を分ける根拠: 読取結果は **もう一度読めば同じものが手に入る**が、
「どう変更したか」 は履歴にしか残らない (ファイルを見ても変更前の姿は分からない)。
再取得可能性が判断の軸である。

`forget-thinking` にも `docs/context-forgetting.md` §10 と同じ
**「実質削減が 0 以下ならロールバック」** を適用する。 小さいツール結果しか
無い場面では、 落とした本文よりトゥームストーンの方が大きくなり得るためである。

### 2.2 `clear` — 引き継ぎを残してリセット

ユーザー要望の「次やることの指示を残して、 一度コンテキストをクリア」 に対応する。

```
1. 現在の履歴から引き継ぎメモを LLM に書かせる
2. セッションを保存し、 **そのセッション ID をユーザーに提示する**
   (`/resume <id>` で完全な履歴に戻れる状態を作ってから消す。 ID を見せなければ
   §8 のリスク対策 (a) は絵に描いた餅になる)
3. history.clear()
4. 引き継ぎメモを最初の user メッセージとして再投入
5. 引き継ぎメモをユーザーにも表示する
```

引き継ぎメモの構造 (テンプレートを固定し、 モデルに埋めさせる):

```markdown
## これまでにやったこと
- (完了した作業を箇条書き。 結論のみ)

## 次にやること
- (未完了のタスク。 最初に着手すべきものを先頭に)

## 守るべき制約・決定事項
- (ユーザーが出した指示、 議論して決まった方針。 **原文に近い形で**)

## 関係するファイル
- path — 何のためのファイルか
```

**「守るべき制約・決定事項」 を独立した節にする**のが要点。 圧縮ではここが
他の情報に混ざって薄まるが、 Clear では履歴が完全に消えるので、 ここが唯一の
拠り所になる。 節を分けて「これは落とすな」 と明示する。

`clear` は **失うものが最大**なので、 既定では確認を取る (§5.2)。

## 3. 区切りの検出

### 3.1 区切りシグナル

`agent-loop` の span 終了 (`purgeEphemeralAtSpanEnd`) と、 ツール実行後に評価する。

| ID | シグナル | 強さ | 根拠 |
|----|---------|------|------|
| B1 | ToDo が **全て completed** になった | **強** | 一連の作業が終わった最も明確な証拠 |
| B2 | `git commit` が成功した (`bash` の結果から検出) | **強** | 本プロジェクトの運用そのものが「作業の区切り毎にコミット」 |
| B3 | Goal Seek の acceptance を満たした | **強** | 目標達成 = 区切り |
| B4 | ToDo が 1 つ `completed` に遷移した (残りあり) | 弱 | 小さな区切り |
| B5 | span が `response_complete` / `final_text_response` で終了し、 かつ完了判定が `completed` | 弱 | `IntentClassifier.classifyCompletion()` の既存判定を流用 |
| B6 | 新しい user 発話が直前の話題と連続していない | 弱 | 話題転換 |

B6 の「連続していない」 は **文字 2-gram の Jaccard 係数 (< 0.12)** で判定する。
`IntentClassifier` に聞くと発話のたびに LLM 呼び出しが増え、 本設計の売りである
「待ち時間ほぼゼロ」 を損なうため、 決定論的な近似で済ませる。 弱い区切りなので
誤検出しても最悪 `forget-thinking` (失うのは読み直せる情報のみ) にしかならない。

**強い区切り**は「前のタスクの詳細をほぼ全部捨ててよい」、
**弱い区切り**は「探索の過程は捨ててよいが、 話の筋は要る」 と解釈する。

### 3.2 山場 (これから重くなる) シグナル

| ID | シグナル | 根拠 |
|----|---------|------|
| P1 | `todo_write` で **3 件以上の pending** を含むリストが新規作成された | これから多段の作業が始まる |
| P2 | plan mode を抜けた (計画 → 実装への移行) | 実装はツール結果で急速に膨らむ |
| P3 | 新しい user 発話が `classifyTaskComplexity() === "complex"` | 既存ヒューリスティックの流用 |

山場シグナルは **区切りシグナルと同時に成立することが多い** (ToDo を作る直前は
たいてい前のタスクが終わっている)。 その場合は「区切りとして整理し、 かつ余裕を確保する」
= より強いアクションを選ぶ。

### 3.3 検出の実装位置

- **B1 / B4**: `todo_write` 系ツール実行の前後で `getTodos()` のスナップショットを比較
- **B2**: `bash` ツールの結果から `git commit` の成功を検出 (コマンド文字列 + exit 0)
- **B3**: Goal Seek の評価結果ハンドラ
- **B5**: `purgeEphemeralAtSpanEnd(reason)` の reason と、 最終テキストの完了判定。
  `response_complete` は **モデル自身の完了宣言**なのでそれ自体を完了判定として扱い、
  `final_text_response` のときだけ `IntentClassifier.classifyCompletion()` の
  **既存呼び出しの結果を控えて流用**する (B5 のために追加の LLM 呼び出しはしない)
- **B6 / P3**: user 発話を受けた時点 (`classifyTaskComplexity` の既存呼び出し箇所 + B6 の 2-gram 判定)
- **P1 / P2**: `todo_write` 系ツール実行後 / plan mode 退出時 (反復先頭で `isInPlanMode()` の変化を見る)

いずれも **既存の通り道にフックを 1 行足す**形にし、 新しいループは作らない。

検出したシグナルは即座に実行せず **待ち行列に積む**。 消費点は 2 つだけで、
(a) 反復の先頭 (閾値チェックの直前)、 (b) span 終了直後 (`run()` の finally) である。
同時に複数立っていたら **より強いものを 1 つだけ**採用する (docs §3.2)。
シグナル検出フックは同期的な場所にもあるため、 この 2 段構えで
「検出は軽く、 実行は安全な地点で」 を実現する。

## 4. 判断ポリシー

### 4.1 決定表

コンテキスト使用率 (`tokens / contextWindow`) と区切りの強さで決める。

| 使用率 | 弱い区切り | 強い区切り | 山場の直前 |
|--------|-----------|-----------|-----------|
| 〜40% | `none` | `none` | `none` |
| 40〜60% | `forget-thinking` | `forget-thinking` | `forget-thinking` |
| 60〜75% | `forget-thinking` | `forget` | `forget` |
| 75%〜 | `forget` | **`clear`** | `compress` |

閾値超過 (`> threshold`) による従来の発火は **そのまま残す**。 区切り整理が
うまく効いていればそもそも到達しない、 という位置付けの安全網である。

### 4.2 なぜこの表なのか

- **40% 未満で何もしない**: 削る必要が無いのに削ると、 情報を失うだけ損である
- **まず `forget-thinking`**: LLM 呼び出しが要らず待ち時間がほぼ無い。
  区切りのたびに実行しても体感を損なわない。 これが第一選択
- **75% + 強い区切りで `clear`**: 「前のタスクが完全に終わって、 かつ枠が苦しい」
  という条件が揃ったときだけ。 最も強い手を最も安全な瞬間に使う
- **山場の直前は `compress`**: 山場では **これから大量に読む**。 `clear` すると
  「何をやろうとしていたか」 の文脈まで薄くなり、 山場の入口で迷子になる。
  要約で圧縮して枠を確保しつつ文脈を保つ方が合う

### 4.3 実行しない条件 (ガード)

以下のいずれかに該当したら **アクションを見送る**。

| 条件 | 理由 |
|------|------|
| 直前のコンテキスト操作から 3 ターン未満 | 連続発火で毎ターン待たされるのを防ぐ (アクション自体を見送る) |
| span の途中 (ツール実行の合間) + `clear` を選んだ場合 | 作業文脈を失い得るため、その回の履歴変更を見送る |
| 未完了の ToDo に `in_progress` がある + `clear` を選んだ場合 | 作業途中なので、その回の履歴変更を見送る |
| Goal Seek 実行中 + `clear` を選んだ場合 | 目標追跡の連続性を優先し、その回の履歴変更を見送る |
| 非 TTY / Discord / Slack 経由 + `clear` を選んだ場合 | 確認が取れないので見送る。**`aggressive` はそもそも確認を取らない**ので対象外 |
| 同じ区切りで一度「何もしない」 を選ばれた + `clear` を選んだ場合 | 同じ質問も別の履歴変更も自動実行しない (§5.2) |

**見送りは必ずログとユーザー通知に出す**。`clear` 失敗を `forget` / `compress` の成功へ置換しない。

## 5. 設定と操作

### 5.1 モード

`config.context.strategy.mode`:

| 値 | 動作 |
|----|------|
| `"off"` | 区切り検出を行わない (従来通り閾値のみ) |
| `"auto"` (**既定**) | 区切りで自動実行。 ただし `clear` は確認を取る |
| `"aggressive"` | `clear` も確認なしで実行 |

既定を `auto` にする根拠: `forget-thinking` は待ち時間がほぼ無く失うものも
「読み直せば取れる情報」 だけなので、 自動で走って困る場面が考えにくい。
一方 `clear` は不可逆に見える操作なので、 既定では必ず人が承認する。

### 5.2 `clear` の確認

TTY のときだけ確認を出す。

```
  区切りを検出しました (ToDo 全完了 / 使用率 78%)。
  引き継ぎメモを残してコンテキストをリセットしますか?

  ❯ リセットする (推奨)
    忘却だけにする
    何もしない
```

「何もしない」 を選んだ場合、 **同じ区切りでは二度と聞かない** (同じ質問が
繰り返し出ると煩わしいため)。

### 5.3 コマンド

| コマンド | 動作 |
|----------|------|
| `/context strategy` | 現在のモードと直近の判断履歴を表示 |
| `/context strategy off\|auto\|aggressive` | モード切替 |
| `/handoff` | **手動で** 引き継ぎメモを作ってコンテキストをリセット |
| `/handoff dry` | 引き継ぎメモを作って表示するだけ (リセットしない) |

`/handoff` を独立コマンドにするのは、 「今ここで区切りたい」 という判断は
ユーザーが一番正確にできるためである。 自動検出はあくまで補助。

`/clear` (履歴全消し) は現状のまま残す。 引き継ぎ無しで完全にリセットしたい
場面もあるため。

## 6. ユーザーへの見え方

アクションが走ったら **必ず 1 行で報告**する。 黙って履歴が変わることがあってはならない。

```
  区切りを検出 (git commit) — 探索の記録を忘却しました (-38,200 トークン / 使用率 71% → 32%)
```

`clear` の場合は引き継ぎメモ全文を表示する。 **何が引き継がれたかを見せずに
履歴を消すのは論外**であり、 メモが不十分ならユーザーがその場で補足できる。

## 8. リスク

| リスク | 対策 |
|--------|------|
| `clear` で必要な情報が失われる | (a) clear 前に必ずセッション保存 → `/resume` で完全復元可能、 (b) 引き継ぎメモを全文表示、 (c) 既定で確認必須 |
| 区切りの誤検出で作業中に発火する | 使用率 40% 未満は `none`。 `in_progress` の ToDo があれば `clear` に行かない。 誤検出しても最悪 `forget-thinking` (失うのは読み直せる情報のみ) |
| 確認プロンプトが煩わしい | 同じ区切りでは再確認しない。 `aggressive` / `off` で切り替え可能 |
| シグナル検出のフックが既存フローを壊す | フックは全て try/catch で囲み、 失敗しても本流を止めない。 コンテキスト整理は付加機能であって本業ではない |
| `git commit` 検出の誤爆 (`git commit --dry-run` 等) | コマンド文字列に `--dry-run` を含む場合は除外。 exit code 0 を必須にする |
| 引き継ぎメモ生成が失敗して履歴だけ消える | **生成成功を確認してから clear する**。失敗時は履歴を保持して報告し、別の整理手段へ切り替えない |

## 9. 将来の拡張余地

- **区切り検出をモデルに任せる**: 現状はヒューリスティック。 「ここは区切りか?」 を
  安いモデル (F1 の named slot) に聞く経路
- **引き継ぎメモの永続化**: `clear` 時のメモをファイルに残し、 セッションを跨いで参照
- **区切りごとの自動チェックポイント**: 既存 `/checkpoint` と連動し、 区切りで
  コード側もスナップショットする
- **効果測定**: 区切り整理の後に「読み直し」 がどれだけ発生したかを記録し、
  決定表の閾値を実データで調整する
