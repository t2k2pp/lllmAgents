## 0. 設計の前提（ユーザー信条）

1. **主用途は実装（Claude Code の代打）**だが、成果物は多様 — コード／文章／PPTX／Excel／調査／書籍執筆／軽い質問・雑談。Claude Code 並みに「目的を察して過不足なく仕上げる」挙動を期待。
2. **抽象化優先**: OneShot/FewShot の具体例を盛るとモデルが引きずられる。「モデルが悩まない最小限まで抽象化」して柔軟性を引き出す。例は *境界を定義する列挙* ではなく *e.g. の最小投与*。
3. ハーネスの存在意義 = **ユーザーの目的を、その目的にふさわしい形で、効率的に高品質に達成させること**。

本設計はこの3点を上位制約として従う。

## 1. 動機 — プローブが暴いた構造欠陥

### 1.1 為替セッションの位置づけ（ターゲットではなくプローブ）

為替確認はユーザーが気まぐれにやった一発タスクであり、**設計が最適化すべき代表タスクではない**。本書は為替を「直す対象」にしない。為替の価値は、**ある構造欠陥を再現可能に露呈させた診断プローブ**である点に尽きる。設計はこの欠陥の構造に対してのみ正当化され、為替頻度には一切依存しない（§7）。

### 1.2 露呈した欠陥（実ログ・コード根拠）

為替セッションで「答えは思考(769字)で既に出ていたのに、ユーザーに届かず3回催促」が起きた。原因は単一サイトのバグではなく、**反応的介入レイヤー全体が「ツール呼び出し＝進捗、テキストのみ＝未完成」という単一の成果物形状を前提にしている**こと。

| サイト (agent-loop.ts) | 文面の前提 | register/intent 認識 |
|---|---|---|
| 共有 `formatSelfCheck` 既定 (self-check-messages.ts:70-71) | 「次の1手は**ツール呼出のみ**」「**テキスト応答単独は進捗と認識しない**」 | なし |
| 空応答 nudge (1339-1352) | 「思考を **ToDo に commit** しろ」 | なし |
| give-up (1363-1364) | **何も返さず終了**（思考に答えがあっても破棄） | なし |
| shouldReprompt (1200-1246) | todo/実装ツール | **あり**（intentClassifier） |
| ToDo未完了ゲート (1373-1399) | todo 完了/response_complete(force) | todo 有無 |

決定的な分裂が2つ:

- **proactive ↔ reactive の矛盾**: システムプロンプトは「explore（成果物なし）＝即答・todo不要」と言う（`lightweight-register-anchors`）。だが reactive 層は「テキスト＝未進捗・todoしろ」と言う。**同じハーネスが正反対を指示**している。
- **main ↔ sub の分裂**: `SUB_AGENT_ACTION_HINT`（self-check-messages.ts:84-86）は既に「**追加作業が不要なら最終回答を出して完了**」とテキスト回答を正当な終端として認める。だが**メインの既定 actionHint だけが**「ツール呼出のみ／テキストは進捗にあらず」。サブは正しく、メインが間違っている。

### 1.3 なぜこれが多様成果物アプリにとって致命的か

成果物は多様（§0-1）。**文章の回答・調査結果・助言は、テキストそのものが正当な成果物**。「ツール＝進捗」前提は、非ファイル成果物を構造的に「未完成」と誤判定し、todo/ツールへ矯正し、最後は無言終了する。実装タスクには正しいが、それ以外を壊す**形状バイアス**である。

## 2. 設計原則（抽象形・例を列挙しない）

反応的介入レイヤーを次の単一原則で統一する。**機構（todo/tool）を指示せず、目的を再提示する**:

> **R1. 目的語は「ツール呼び出し」ではなく「ユーザーの目的の可視的前進」。** 成果の *形*（テキスト回答／ファイル／検証結果）は目的が決める。ハーネスは一形状に固定しない。
>
> **R2. 前進が無いときの介入は、機構を指示せず目的を再提示する。** 「todo を作れ／ツールを呼べ」ではなく「この依頼に対し、ふさわしい形で可視的な結果を出したか？ 答えが出ているなら答えを、作業が要るなら実行を」。形の選択はモデルの register 判断に委ねる（proactive 層と同一思想）。
>
> **R3. 捏造・偽装をしない（信頼の絶対防衛線）。** 禁じるのは *フォールバック全般* ではなく **捏造**: 失敗を隠して劣化代替を答えにする／provenance を偽る（プログラム生成を「モデルの応答」と言う、依頼していない委任を「した」と言う 等）。一方で **粘り強いリトライ** と **パーサによる実意図の吸収**（厳格 JSON を出せない応答の救済等）は捏造ではなく *許容・推奨*（ユーザー信条 [[feedback_no_fabrication]]）。失敗が避けられないときは **正直に・具体的に失敗報告して止まる**（無言終了＝隠蔽も NG、偽の結果＝捏造も NG）。何かを「X した／X の出力だ」と述べるのは実際に X が起きたときだけ。
>
> **R4. 完了圧（過小納品の防止）は維持するが、形状中立にする。** drawDot トラウマ由来の「promise だけで止まるな」は残す。ただし「進捗＝ツール」ではなく「進捗＝目的への可視的前進（答えも含む）」と定義し直す。
>
> **R5. 可視性（ハーネスの機械的責務）と 品質・promise 判定（モデル＋既存分類器の責務）を分離する。** ハーネスが機械的に見るのは「**このターンに可視的な実体出力が1つでもあるか**（非空テキスト or ツール呼出 or 完了宣言）」だけ。無ければ surface する。ハーネスは「これは promise か実答か」「答えの質は十分か」を**判定しない**（それはモデル＋既存 intent 分類器の役目）。これにより、弱モデルに**新たなメタ認知（自己分類）を要求しない**。

この5原則は具体例（じゃんけん/為替/PPTX…）を一切含まない。モデルが register（explore/rough/standard/production）を判断する材料は proactive 層に既にあり、reactive 層はそれと**矛盾しないこと**だけを担う。

### 2.1 tier 非依存であること（BYOM 前提）

tier 解決は best-effort の推測である（`capability-tier.ts:270-329`: 完全一致 → 名前パターン → 名前のサイズ表記ヒューリスティック → **T2 フォールバック**）。BYOM で任意のローカル LLM が繋がる構成では、**システムはモデルの強さを事前に知り得ない**。したがって:

- **本設計の核（R1–R5）は tier に依存してはならない。** 誤分類されても正しく動くこと。
- R5 の通り、ハーネスが見るのは**機械的シグナル**（テキスト空か／思考があるか／promise パターンに一致するか）であって、**モデルの自己分類能力ではない**。これは tier に依存しない（強弱どちらでも文字列判定は同じ）。
- tier に依存するのは「弱モデル向けの最小例を 1 個足すか」という**非・負荷的な味付け**のみ（§3.2）。誤分類しても、最悪「例が 1 個多い/少ない」だけで核の正しさは揺らがない。

## 3. 抽象化 vs 具体例 の方針（ユーザー信条 §0-2 への準拠）

### 3.1 原則

- 介入文面・原則は**抽象命題**で書く。境界を定義する**列挙はしない**。
- 例は「弱モデルが抽象だけでは本当に悩む箇所」に限り、**「e.g.」明示の最小1例**に留める（universe を定義する列挙にしない）。

### 3.2 tier 留保（ただし非・負荷的）

リポジトリの tier 設計では T3（弱いローカル LLM）が `verbose+examples`。抽象命題だけだと弱モデルが判別できず過小に倒れる懸念がある（drawDot）。折衷:

- **強モデル（T1）**: 抽象原則のみ。例は過適合の毒なので置かない。
- **弱モデル（T3）**: 原則＋**最小1例**。ただし例は「答えを返す形もある」ことを示す *対称化* の1例であって、特定タスク（為替等）の列挙ではない。

**ただし §2.1 の通り、tier は推測でしかない（BYOM では特に）。** よってこの最小例は**核の正しさを左右しない味付け**に留める。誤分類への安全側として:

- 未知 BYOM の既定は T2 フォールバック（`capability-tier.ts:322-328`）。例の付与は「過小支援の害 ＞ 過剰支援の害」（強モデルは冗長な例を無視できるが、弱モデルは例が無いと壊れる）の非対称を踏まえ、**迷ったら例を付ける側**に倒す。これは抽象化信条（§0-2）と衝突するように見えるが、衝突しない: 付けるのは*1個の e.g.*であって列挙ではなく、強モデル（T1）には付けない。

### 3.3 既存 register アンカーの再検討（自己整合）

先行の `lightweight-register-anchors-design.md` 実装は判定木に **じゃんけん/占い/サイコロ/挨拶/雑談** と**具体例を列挙**した。これは §0-2 の「引きずらない＝抽象化」と相反する。本設計の一部として、これを**抽象命題＋最小例へ削る**改修を含める:

- 改修前（列挙）: 「会話・遊び・一発回答 (じゃんけん/占い/サイコロ/挨拶/雑談) → そのまま答える」
- 改修後（抽象）: 「**成果物（ファイル等）を作らず答えれば済む依頼は、そのまま簡潔に答える**（例: 雑談・即答質問）」 ← 例は e.g. 1 個のみ

T3 版のみ最小例を残し、T1/T2 は抽象命題に寄せる。

## 4. 仕様（共有レイヤーを直す＝サイト個別パッチにしない）

サイトごとに文面をいじるのではなく、**共有の文面生成と少数の終端経路**を直し、全サイトに一括で原則を効かせる。

### 4.1 `formatSelfCheck` の既定 actionHint を形状中立化（self-check-messages.ts:68-71）

メイン既定を、サブ用 `SUB_AGENT_ACTION_HINT` と同じ思想（テキスト回答も正当な完了）へ統一:

```
（改修案）既定 actionHint:
  「次の 1 手: 依頼にふさわしい形で可視的な結果を出す。
   ・答えが既に出ているなら、そのまま回答を出して完了（メインは response_complete、サブは最終回答）
   ・作業が要るなら該当ツール（file_write / bash / mcp__... 等）を呼ぶ
   ・promise テキスト（「了解」「実装します」）だけでは進捗と認識しない」
```

「テキスト応答単独は進捗にあらず」という形状バイアス文を削除し、「**promise だけが進捗にあらず**（＝中身の無い宣言を弾く）」に意味を絞る。これで promise ループ防止（本来の目的）は維持しつつ、**中身のある回答テキストは正当**になる。

### 4.2 空応答 nudge を「目的再提示」へ（agent-loop.ts:1339-1352）

todo 中心の列挙をやめ、R2 の目的再提示に置換。思考に結論がある場合を最優先で扱う:

```
（改修案）空応答 nudge:
  「thinking は記録されましたが、ユーザーに見える結果がありません。
   ・思考の中で結論が出ているなら → それを回答テキストとして出力（必要なら response_complete）
   ・まだ作業が要るなら → 計画(todo_append) もしくは実装ツールを呼ぶ
   元依頼: {intent}」
```

「ToDo に commit」を*第一選択から外し*、「結論があるなら答えを出す」を先頭に。これが proactive の explore 即答と整合する。`strategic-todo-design.md §3.3`（todo 中心 nudge）は本書で**形状中立へ更新**する（§9 に相互参照を記録）。

### 4.3 give-up — 根本原因除去＋粘り強さ＋正直なエラー（捏造しない）（agent-loop.ts:1357-1364）

**方針（[[feedback_no_fabrication]] 準拠）**: give-up に対して「思考を scrape して疑似回答にする」のは **捏造**（provenance 偽装＝信頼破壊）なので**しない**。一方でリトライ（粘り強さ）は捏造ではなく*推奨*。3段で対処する:

**(i) 根本原因を断つ（本命）**
為替ケースの give-up は「答えは思考にあるのに、todo 中心 nudge（§4.2）に誘導され可視出力が出ず、リトライ上限で無言終了」だった。**§4.1–4.2 の形状中立化（proactive/reactive の矛盾解消）と R5 の可視性原則を入れれば、答えが存在するケースはそもそも give-up に到達しない**（モデルは「答えがあるなら出す」と促され、実際に出す）。これが第一の、そして主要な対策。取り繕う対象が**消える**。

**(ii) 粘り強くリトライする（捏造ではない・推奨）**
1 回の空応答で「ダメでした」としない。通信エラーのリトライと同じく、目的達成のための粘りを持つ。リトライ回数・原因の観測（各空応答が「なぜ起きたか」）はログに残し、別件として調査の余地を残す。※リトライ上限値（現 `MAX_EMPTY_RETRIES`）が「粘り強さ」として妥当かは実装時に観測して調整。

**(iii) それでも本当に到達したら、正直に失敗報告して止まる（捏造・隠蔽の両方なし）**
context 溢れ・フォーマット完全崩壊などで真に到達した場合:
- **偽の回答・劣化代替を差し込まない／provenance を偽らない**（思考 scrape を「答え」と称さない、やっていない委任を「した」と言わない）。
- **正直で具体的な失敗報告**を返す: 何回試みたか・推定原因（連続空応答 N 回／context 長超過の兆候）・次の一手（再試行 / モデル変更 / 入力短縮）。
- 生の思考は**疑似回答として出さない**。必要な人向けに「詳細は LLM ログ（`llmLogger`）に保全済み」と案内するに留める。
- **無言 return（現行の何も返さず終了）は廃止**（沈黙＝隠蔽）。
- **新規 LLM 呼び出しはしない**（壊れている状態での追加呼び出しは無意味）。

整理: 「無言終了（隠蔽）」も「疑似回答（捏造）」も NG。リトライ（粘り）は OK。最終的に残る正解は **honest failure 報告**。

### 4.4 register/intent 認識の一貫化

`shouldReprompt` は既に intentClassifier を持つ（1208）。空応答経路・give-up 経路は持たない。**完了判定（classifyCompletion）を空応答経路でも軽く使う**か、少なくとも §4.1-4.3 の形状中立化で「intent を知らなくても誤らない」状態にする（形状中立なら intent 不明でも壊れない＝より頑健）。本設計は **「intent 認識を全サイトに配る」より「文面を形状中立にして intent 非依存で正しくする」を優先**（抽象化優先・依存を増やさない）。

## 5. drawDot（過小納品）非回帰の担保

本設計は explore 側に倒すが、**過小納品を再発させない**線引きを明示する:

- 維持: 「promise だけ（中身の無い宣言）で止まる」検出と nudge（§4.1 で意味を *promise* に絞って維持）。
- 維持: 実装タスクで**未完了 todo があるのにテキストで終わろうとする**ゲート（1373-1399）。これは「成果物＝ファイル」が明示されている文脈なので形状バイアスではなく*正当な完了基準*。手を入れない。
- 変更するのは「**成果物形状が未確定／成果物なしの文脈で、テキスト回答を一律 *未進捗* 扱いする**」部分のみ。
- 結果、実装タスク（drawDot 型）の完了圧は不変、explore/回答タスクの誤矯正のみ解消。

## 6. タスク種別マトリクス（**設計入力ではなく回帰検証専用**）

設計を以下に**寄せない**。これは「他タスクを壊していないか」を確認する*検証チェックリスト*であり、為替はその1プローブ行に格下げ。

| タスク種別（成果物） | 期待挙動 | 検証観点 |
|---|---|---|
| 実装（ファイル＋検証）= 主用途 | todo/実装/検証で完了。未完了ゲート有効 | **drawDot 非回帰**（§5）。完了圧が落ちていないこと |
| 文章/PPTX/Excel/書籍（ファイル） | ファイル生成＋完了。テキスト宣言だけで終わらない | promise ループ防止が維持されること |
| 調査→回答（テキスト成果） | 調査ツール後、**答えをテキストで返して完了**。todo 強制されない | 形状中立化が効くこと |
| 即答質問・雑談（テキスト） | ツールも todo も無しで即答完了 | proactive/reactive 整合。無言終了しない |
| 〔プローブ〕為替（テキスト） | 思考の結論がテキストで surface され1ターンで完了 | §1.2 の再現が解消すること |

## 7. 頻度依存／非依存の分解（正当化の明確化）

- **頻度非依存（explore が稀でも直すべき構造欠陥）**: ①無言 give-up（全タスクで、モデルが思考だけ吐いた瞬間に起きうる）②proactive/reactive 矛盾③main/sub 文面分裂。→ 本設計の背骨。
- **頻度依存（explore/回答タスクが実在して初めて便益）**: 空応答 nudge の「答えを出す」優先付け。ユーザーは「軽い調査・質問もする」と明言（§0-1）。→ 便益あり、ただし背骨はこれ抜きでも成立。

## 9. 評価 — 成功基準

1. **形状中立の単体性**: 共有 actionHint・空応答 nudge に「テキスト＝未進捗」系の語が無いこと（文字列テスト）。
2. **無言終了の排除**: 思考のみ＋リトライ上限で、ユーザーへ非空のメッセージが必ず返ること（テスト）。
3. **drawDot 非回帰（最重要）**: 実装タスクで未完了 todo ゲート・promise ループ防止が従前どおり働くこと（既存テスト＋追加）。
4. **proactive/reactive 整合**: explore 相当の入力で、reactive 層が todo を強制しないこと。
5. **回帰**: 既存 vitest 全 pass。
6. **e2e（ユーザー環境）**: 為替プローブ再走で思考の結論がテキスト化され1ターン完了（実モデルが要るためユーザー検証）。
7. **tier 非依存性**: tier を T1/T2/T3 で切り替えても、空応答 surface・無言終了排除の*核挙動*が同一であること（機械的シグナル依存のテストで担保）。
8. **give-up は honest failure のみ（捏造・隠蔽なし）**: 疑似回答（思考 scrape 等）を差し込む経路が無いこと、provenance を偽る記述が無いこと、無言 return が無いこと、新規 provider 呼び出しが無いこと（コードレビュー＋テスト）。失敗時は具体的理由を含む明示メッセージのみ。リトライ（粘り）は別途許容。

## 10. リスク

| リスク | 緩和 |
|---|---|
| explore に倒しすぎ→過小納品再発 | §5 の完了圧維持。マトリクス§6で実装行を必須検証 |
| 抽象化しすぎ→弱モデルが判別不能 | §3.2 の tier 留保（T3 のみ最小1例） |
| **tier 誤分類（BYOM で強さ不明）で挙動が崩れる** | §2.1: 核 R1–R5 は tier 非依存（機械的シグナルのみ）。tier 依存は非・負荷的な最小例だけ。誤分類でも核は不変。ユーザー override も既存（`CapabilityOverride`） |
| **give-up を疑似回答フォールバックで取り繕う＝誤魔化し** | §4.3: フォールバックを**作らない**。根本原因除去（§4.1-4.2）で経路自体を稀にし、到達時は **honest failure 報告のみ**（偽結果なし・無言なし・新規 LLM 呼出なし） |
| 既存 strategic-todo §3.3 の意図（todo commit 誘導）との齟齬 | §9 で相互参照、§4.2 で「形状中立へ更新」と明記し設計史を残す |
