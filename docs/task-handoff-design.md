## 1. 背景 (2026-11-07 の実機セッション)

`~/.localllm/logs/sessions/2026-11-07T22-20-27_main.jsonl` (Qwen3.8 Flash Next、 contextWindow 131,072。 Blender で猫を作る依頼) が、
整理イベント r-25 / r-28 の失敗 (`still-too-large` / `nothing-to-summarize`。 「整理後の推定 P 107,928 + 最低限の予約 25,067 > contextWindow 131,072」) で止まった。

最後の送信の中身:
- `<summary-of-earlier-turns>` が 21 個、 合計 約 115,000 文字。 どれも「# Summary of the conversation so far」 から全体を書き直したもの
- system の「[忘却の記録]」 が 約 20,000 文字

原因 (`src/agent/reduction-summary.ts`):
1. `selectSummaryRange` は最後の既存の要約の次から範囲を選ぶ (要約を要約し直さない)。 要約は増える一方
2. `classify()` は system ノートと利用者の発言をいつも残す
3. よって整理の後の床 (それ以上減らせない量) が 68K → 85K → 92K → 100K トークンと単調に上がった

その後、 利用者が別の依頼 (狼) を出したとき `boundary:new-request` は動いたが、 `reduction_skipped / below-minimum`
(見込み 11,880 < 最低量 32,768) で見送られた。 ほぼ全部が消せない要約・ノートだったため。 猫の依頼は中断で終わったので `request-end` も通っていない。

要約の要約を重ねる限り、 世代ごとに薄まり、 しかも床が上がる。 そこで **タスクごとの引き継ぎ文書をディスクの正本にし、 文脈にはそこから毎回抜き出し直した抜粋だけを置く** (要約の要約をしない) ことにした (2026-11-08 利用者と合意)。

## 2. 目標と非目標

目標:
- タスク (依頼のまとまり) ごとに 1 つ、 決まった節を持つ引き継ぎ文書をディスクに置き、 区切りと整理の前に更新する
- 話題が変わったら、 前のタスクを文書に閉じ (中断 / 完了)、 文脈には 1 行の指し示し (ポインタ) だけを残す。 最低量 F に届かなくても畳む
- 手動の `/handoff` のメモを、 この文書から描く (利用者向けの描画)。 利用者が書いた引き継ぎファイルは入力としてだけ読む
- (第 2 段) 整理の中で、 溜まった要約を文書から抜き出し直した抜粋 1 つに置き換える

非目標:
- 要約 (段階 3) を無くすこと。 第 2 段では、 使っている文書があるときは段階 3 を抜粋で行い (整理の前の文書の更新が要約の代わり)、
  文書が無い・判断の節を直せなかったときは今までどおり要約を使う (§9.6)
- 文書を利用者が手で編集する前提の書式 (正本は JSON。 §4.1)

## 3. 段階の分け方

| 段 | 内容 | 状態 |
|---|---|---|
| 第 1 段 | 文書の作成・更新・閉じる (節の上限・経緯ログ)、 区切り (ToDo 全完了・依頼の終わり・新しい依頼・整理の前) での書き込み、 新しい依頼での前のタスクの 1 行への畳み込み (最低量を見ない)、 `/handoff` を文書から描く | 実装済み (本書 §4〜§8) |
| 第 2 段 | 整理イベントの段階 3 で、 溜まった `<summary-of-earlier-turns>`・忘却の記録・今のタスクのやり取りを、 文書から抜き出し直した抜粋 1 つに置き換える。 忘却の記録に上限 | 実装済み (本書 §9) |

## 4. 文書

### 4.1 置き場所と形

| もの | 場所 | 役目 |
|---|---|---|
| 正本 | `~/.localllm/sessions/<セッション ID>.tasks/<タスク ID>.json` | 機械が読み書きする正本 (版 `version: 1`) |
| 読む形 | 同じフォルダの `<タスク ID>.md` | 正本を保存するたびに描き直す。 ポインタ・`/handoff` のメモが指すのはこちら (モデルが `file_read` で読める) |
| 経緯ログ | 同じフォルダの `<タスク ID>.history.md` | 追記だけ。 文脈には載せない。 上限で押し出した「決めた事」・削除した決まり (理由つき)・閉じた記録 |

- セッションの保存先 (`~/.localllm/sessions/<id>.json`) の隣にしたのは、 セッションと一緒に消す・移すときに一緒に扱えるようにするため。 パスはすべて絶対パス
- 正本を JSON にしたのは、 「依頼の原文」 が利用者の文をそのまま持つため (原文に `## ` があると Markdown の節で読み戻せない)
- タスク ID は `t-<時刻 36 進>-<乱数 4 桁>`
- セッションには使っているタスクの正本のパス (`SessionData.taskHandoff.activeDocPath`) だけを保存し、 `/resume` で読み戻す。 読めなければ黙らず警告し、 使わない (次の依頼の始まりで作り直す)

### 4.2 節 (決まった 7 つ)

| 節 | 更新のしかた | 上限 |
|---|---|---|
| 依頼の原文 | 利用者の言葉をそのまま追記 (依頼の始まり・途中の追加入力)。 **要約しない** (薄まりの錨) | 無し (ファイルには全文。 抜粋では §9.2) |
| 決まり・制約 | 追記。 削除は理由が要る (理由の無い削除は無視して経緯ログに残す。 削除したものも理由と一緒に経緯ログへ) | 1 項目 400 字。 40 項目を超えたら経緯ログに警告 (自動では消さない) |
| 現状 | 毎回書き直す | 2,000 字 |
| 決めた事と理由 | 追記 | 12 項目 × 300 字。 溢れた古いものは経緯ログへ |
| 試して駄目だった事 | 追記 (同じ文は重ねない)。 例: ツールが切れていた・API キーが無い | 15 項目 × 300 字。 溢れた古いものは経緯ログへ |
| 次の一手 | 毎回書き直す | 1,200 字 |
| 関係するファイル | ツール呼び出しの引数 (`file_path` / `path` など) から機械的に足す | 30 件 (新しい順。 溢れた古いものは落とす) |

ほかに、 機械的に毎回写すもの: ToDo の状態 (「現状」 の下に描く)、 状態 (`進行中` / `中断` / `完了`)、 作成・更新の時刻、 最後の更新の契機。

### 4.3 書く時期

| 契機 | LLM で判断の節を直すか (§4.4) | 備考 |
|---|---|---|
| ToDo が全部完了 (`todos-complete`・`goal-achieved`) | 前回から後にツール呼び出しがあったか、 増えた分が 2,000 字以上のとき | 本体呼び出しの直前 (`judgePendingBoundary`) |
| 依頼の終わり (`request-end`) | 同上 | 正常に終わったとき。 中断・エラーのときは LLM を呼ばず機械的な節だけ写す |
| 新しい依頼 (`new-request`) | 前のタスクを閉じるときは必ず | §5 |
| 整理の前 (`before-reduction`) | 必ず (増えた分があれば) | 整理イベントが履歴を差し替えると決め、 差し替える直前。 **書いてから落とす** (§6) |
| `/handoff` | 必ず | §7 |

### 4.4 判断の節の更新 (脇の呼び出し `task-handoff`)

- 送り方は段階 3 の要約と同じ「本体と同じ並び + 指示」 (`buildMainCallRequest()` の後ろに指示の user を 1 件足す)。
  サーバは本体の並びの KV キャッシュを使えるので、 読み直しは指示の分だけで済む。 モデルは要約の抜粋でなく文脈の全体を見られる
- 指示には今の文書 (正本の描画) と「前回の更新より後に増えたメッセージの件数」 を入れ、 **変わった節だけ** を決まった形で返させる (§4.5)。
  変わらない節は書かせない (出力を小さくする)。 何も変わらなければ `変更なし`
- 「前回の更新より後」 はメッセージの同一性 (`WeakSet`) で数える。 再開の後は全部が新しい扱い
- 思考はそのまま (本体と同じ送り方を揃えるため)。 出力上限は min(出力の上限 O, W − P − 指示 − M)。 1,000 トークン未満なら `no-room` で呼ばない
- ツールを呼んだ・形が違うときは 1 回だけ出し直す。 出力上限で切れたものは受け取らない
- レート制限はそのまま投げる (再試行しない。 AGENTS.md「LLM execution and rate limits」)。 そのほかの失敗は、 機械的な節だけ書いて結果に失敗を載せる (呼び出し側の扱いは §5・§6)

### 4.5 更新の返させ方

```
## 決まり・制約
+ 足す決まり (利用者の言葉に近い形で)
- 削除する決まり (今の文書のとおり) | 理由: なぜ外すか
## 現状
(書き直した本文)
## 決めた事と理由
+ 決めた事 — 理由
## 試して駄目だった事
+ 試した事 — 駄目だった理由
## 次の一手
(書き直した本文)
```

## 5. 新しい依頼での畳み込み (`new-request`)

`run()` の始め (新しい発言を履歴に入れる前、 規則 2 の `new-request` の判定より前) に行う。

1. 使っている文書が無く、 履歴に (ポインタ以外の) 中身があるとき: 履歴の利用者の発言から文書を作る (前のタスクに文書がまだ無いときに先に作る)
2. 新しい発言が前のタスクの続きか、 別のタスクかを決める
   - 続きの印 (`続けて` `もっと` `さっき` `それ` など) で始まる短い発言は、 LLM を呼ばずに続き
   - それ以外は脇の呼び出し `task-switch` (思考オフ。 前のタスクの原文と現状と新しい発言だけを送る小さな呼び出し) で `same` / `new`
   - 分類に失敗したら (レート制限を除く) 畳まずに続きとして扱い、 警告を出す (履歴を消す側には倒さない)
3. 続きなら: 新しい発言を「依頼の原文」 に追記する (状態は `進行中` に戻す)
4. 別なら:
   1. 前のタスクの文書を更新 (§4.4) し、 閉じる。 状態は、 そのタスクの最後の依頼が正常に終わり未完了の ToDo が無ければ `完了`、 ほかは `中断`
   2. 今のセッションを別のセッションとして保存し (`/handoff` と同じ。 `/resume <ID>` で畳む前に戻れる。 ID は文書の `archivedSessionId`)、
      履歴をポインタのメッセージ 1 件に置き換える (書き換え理由 `task-fold:<ID>` を申告。 cache_miss では整理イベントと同じく想定どおり)
   3. 新しい依頼の文書を作る
   - 失敗したときは **畳まない** (履歴は元のまま。 警告を出し、 規則 2 の判定へ進む)。 レート制限なら依頼を止める (新しい発言は履歴に入れない)
     - 1 の判断の節の更新が (レート制限以外で) 失敗: 前のタスクは機械的な節だけ書いて閉じ、 新しいタスクの文書を作る (履歴は残るので、 前のタスクの中身は通常の整理に任せる)
     - 文書の保存か 2 のセッションの保存が失敗: 前のタスクの文書を使い続ける (閉じない・新しい文書も作らない)
- 畳み込みは整理イベントではないので、 最低量 F (`below-minimum`) を見ない。 畳んだ後の P は小さいので、 続く `new-request` の判定はふつう発火しない
- ポインタのメッセージ (user。 先頭に `[タスクの記録]`):

```
[タスクの記録] 前のタスクは引き継ぎ文書に移しました。 続きや詳細が要るときは file_read で読んでください。
- 猫をBlenderで作って: C:\Users\…\.localllm\sessions\<id>.tasks\t-….md（中断）
```

  これまでのポインタの行は残し、 新しい行を後ろに足す (多くても 20 行。 古いものから落とす。 文書は残る)

### 5.1 ポインタの置き場所と前方一致

- 畳み込みは system の後ろの履歴を全部書き換えるので、 ポインタは履歴の先頭 (system の直後) に置く。 書き換えの借りは 1 回で、 その後の送信は前方一致を保つ
- ポインタは利用者の発言の扱い (user) なので、 段階 0〜3 の整理では消えない (`classify()` が残す)。 先頭にあるので、 整理で後ろが書き換わってもポインタの前は変わらない
- 次の畳み込みでポインタのメッセージを作り直すのは、 どうせ全体を書き換える時だけ
- 走っている先読みは切る (`PREWARM_ABORT_REASONS.reduction`)。 増分 G には減らした量を足し戻す

## 6. 整理の前の書き込み (`before-reduction`)

- `runReductionEvent` の入力に `beforeRewrite?: () => Promise<TaskHandoffDoc | null>` を足した (第 2 段で書いた文書を返すように広げた)。 履歴を差し替えると決まり、 写しの検証まで済んだ直後、
  `replaceMessages()` の直前に 1 回呼ぶ (段階 3 の要約の呼び出しより後)。 第 2 段の抜粋の道では、 段階 3 の代わりに抜粋を描く直前に呼ぶ (§9.3)。 見送り・減らせない (`nothing-to-reduce`)・入らない (`still-too-large`) では呼ばない
  (規則 1 は減らせなくても毎回の呼び出しの前に判定するので、 その度に脇の呼び出しをしないため)
- 投げたら整理イベントは失敗 (`task-handoff-failed`。 履歴は元のまま)。 AgentLoop は次の場合に投げる:
  - 文書の保存に失敗した (書けないまま落とさない。 `handoff.ts` と同じ約束)
  - レート制限
- 判断の節の更新が (レート制限以外で) 失敗したときは、 機械的な節を書いたうえで投げない (要約がある整理を止めると、 規則 1 では作業が止まるため)。
  失敗は警告と記録 (`task_handoff`) に出す。 このとき `beforeRewrite` は null を返し、 整理は抜粋を使わず要約の動作にする (古い現状の抜粋で落とさない。 §9.6)

## 7. `/handoff` との関係

- システムの文書が唯一の正本。 `/handoff` のメモはその描画 (`renderHandoffNoteFromTask`)
  - これまでにやったこと ← 現状・決めた事
  - 次にやること ← 次の一手 (無ければ未完了の ToDo)
  - 守るべき制約・決定事項 ← 依頼の原文 (原文のまま)・決まり・制約・試して駄目だった事
  - 関係するファイル ← 文書のパス (正本) と関係するファイル
- `/handoff` と `/handoff dry` は、 使っている文書があれば更新 (§4.4) してから描く。 更新か保存に失敗したら、 メモを作れなかった扱い (履歴は変えない。 handoff-design.md §3 の約束のまま)。
  文書が無ければ (機能が切れている・まだ依頼が無い) これまでどおり LLM にメモを書かせる
- `/handoff from-file <path>` (利用者が書いたファイル) は入力としてだけ読む: 「守るべき制約・決定事項」 の項目を文書の「決まり・制約」 に写し、
  リセットの手順はこれまでどおり。 利用者のファイルをシステムの正本にはしない
- リセットの後も同じタスクの文書を使い続ける (メモの user は依頼の原文に入れない)

## 9. 第 2 段: 要約を抜粋に置き換える (2026-11-08 実装)

### 9.1 やること

整理イベントの段階 3 (段階 0〜2 だけでは目標・最低量に届かないとき。 手動の `/compact` は常に) で、 使っている文書があれば、
段階 0〜2 の後の写しのうち **先頭のポインタの後ろから保護部分の手前まで** を、 文書から**毎回抜き出し直した**抜粋 1 件
(user。 先頭 `<task-handoff-excerpt`) に置き換える。 要約の LLM 呼び出しはしない (整理の前の文書の更新 §6 が、 本体と同じ並びで文脈の全体を見て判断の節を直すので、 それが要約の代わり)。
抜粋は文書から作るので、 何回整理しても世代で薄まらず、 大きさは節の上限で決まる (床が上がらない)。

保護部分は段階 3 の要約と同じ (`protectedTailStart`: 直近 K 回のツール呼び出しと最新の応答の組)。 ただしツール呼び出しの無い履歴で保護部分の頭が
要約・前の抜粋・忘却の記録 (作り直せる派生物) のときは、 それも範囲に入れる (2026-11-07 の形は要約しか無く、 最後の要約が保護部分に残ってしまうため)。

### 9.2 範囲の中の扱い (2026-11-08 決定)

| もの | 扱い | 理由 |
|---|---|---|
| ポインタ (`[タスクの記録]`) | 残す (範囲の外の先頭。 中にあっても残す) | 前のタスクへの道。 先頭が変わらないので前方一致もそこまで保つ |
| 既存の要約 (`<summary-of-earlier-turns>`) | 落とす | 抜粋が文書から作り直す。 要約の要約をしない |
| 前回の抜粋 | 落とす (新しい抜粋 1 件に置き換える) | 抜粋を積まない。 毎回作り直す |
| 忘却の記録 (system `[忘却の記録]`) | 落とし、 行は抜粋の末尾の「忘却の記録」 に直近 12 行だけ写す (古い行は「これより前の N 行は省略」 の数に足す) | 際限なく伸ばさない (§9.5) |
| 利用者の発言 (文字だけで、 文書の「依頼の原文」 に同じ文がそのまま入っているもの) | 落とす | 原文は文書が持ち、 抜粋にもそのまま載る (§9.4)。 残すと長いタスクで床が上がる |
| 利用者の発言 (文書に無い・画像付き) | 残す (元の順で抜粋の後ろ) | 文書に無い言葉・画像を黙って消さない |
| ハーネスの促し (揮発の user)・モデルの発言・ツールの組 | 落とす | 判断の節 (現状・決めた事・試して駄目だった事・次の一手) は直前の更新で文書に入っている。 ToDo は機械的に写してある |
| `ask_user`・`enter_plan_mode`・`exit_plan_mode` の組 | 残す | 利用者の答え・承認。 文書の節に機械的には写らない |
| そのほかの system ノート | 残す | 知らないものは消さない |

利用者の発言を落とす判断: 落とすのは「依頼の原文」 に一字一句同じ文があるものだけ。 依頼の始まりより後の追加入力 (割り込みの追加入力・続きの発言) も
`noteFollowUp` で原文に追記されるので、 原文として残る。 さらに整理の前の更新の指示に「依頼の後に利用者が足した指示・制約は必ず『決まり・制約』 に足す。
整理のとき原文の発言は履歴から外れ、 抜粋だけが残る」 と書いた (抜粋の原文は字数で頭だけになることがあるため、 決まりとしても残す)。

### 9.3 流れ (`runReductionEvent`)

1. 段階 0〜2 を写しに当てはめる (今までどおり)
2. 段階 3 が要るなら、 入力の `taskExcerpt.peek()` (使っている文書。 無ければ履歴から作る保存しない仮の文書) で範囲と抜粋の大きさを見込む (`planTaskExcerpt`)。
   減るなら抜粋の道、 減らない・文書が無いなら要約の道 (記録 `taskExcerpt` に fallback の理由)
3. 規則 2 はこの見込みで最低量 F に届くか決める (届かなければ見送り。 文書は書かない)
4. 抜粋の道: `beforeRewrite()` で文書を書き (判断の節を直す)、 **返った文書から** 範囲を決め直して抜粋を描き、 写しを置き換える。
   忘却の記録は抜粋の末尾に写したので system の記録は足さない。 `beforeRewrite` が null (判断の節を直せなかった) なら要約の道に切り替える (文書は書いたので、 差し替えの前にもう一度は書かない)
5. 以降は今までどおり (still-too-large の検査・ツールの対の検証・`replaceMessages(next, "reduction:<ID>")` の 1 回)

AgentLoop は、 今の依頼の始まりの発言を抜粋に任せて落としたとき、 抜粋のメッセージを今の依頼の始まり (前処理の境目) にする。

| 口 | 中身 |
|---|---|
| `ReductionEventInput.beforeRewrite` | `() => Promise<TaskHandoffDoc \| null>`。 書いた文書を返す (判断の節を直せなかったときは null) |
| `ReductionEventInput.taskExcerpt` | `{ peek, mdPathOf }`。 AgentLoop は `TaskHandoffTracker.peekDoc(history)` と `store.pathsFor(doc).md` を渡す。 タスクの引き継ぎが切れていれば渡さない (要約だけ。 記録は `not-used`) |
| `src/agent/reduction-excerpt.ts` | `planTaskExcerpt` (範囲と内訳・忘却の記録の行)・`applyTaskExcerpt`・`renderExcerptMessage` (純粋) |
| `renderTaskHandoffExcerpt(doc, mdPath, requestChars, forget)` | 抜粋の本文 (§9.4) |

### 9.4 抜粋 (`renderTaskHandoffExcerpt`)

- 先頭に「ハーネスが置いた記録で、 利用者の新しい発言ではない」 旨と文書のパス
- 依頼の原文: 最初の依頼 (錨) を先に、 次に新しい追加から古い方へ合計 6,000 字まで配る (描くのは元の順)。 入らない途中の追加は「ほか N 件の追加は文書の全文を読む」、 途中で切れたものは「… (続きは文書)」
- 決まり・制約・現状 (+ ToDo)・決めた事・試して駄目だった事・次の一手: 全部 (上限内)
- 関係するファイル: 最近の 10 件
- 忘却の記録 (あれば): 直近 12 行と省いた行の数

置き方を user にしたのは、 依頼の原文 (利用者の言葉) を持つためと、 履歴の途中の system を受け付けないテンプレートがあるため (要約を assistant に置いた理由と同じ問題を避ける)。

### 9.5 忘却の記録の上限

- 抜粋の道: system の忘却の記録は範囲の中なら落とし、 行を抜粋の末尾に写す (直近 12 行。 `EXCERPT_FORGET_LINES_KEPT`)。 前回の抜粋の行と省いた数も引き継ぐ
- 段階 0〜2 だけの整理・要約の道 (文書が無いとき): `insertTombstone` が追記した記録を直近 4 回分 (`TOMBSTONE_BLOCKS_KEPT`) だけ残し、 それより前は
  「それより前の整理 N 回分の記録は省略しました」 の 1 行にする (`capTombstoneBlocks`)。 長い 1 つのタスクで記録が際限なく伸びない

### 9.6 文書が使えないとき (要約の動作のまま)

記録 `reduction_event` の `taskExcerpt` に出す (`/compact` の結果・`/context` の直近の整理・動作ログの警告にも出る):

| `taskExcerpt.status` | いつ |
|---|---|
| `not-used` | タスクの引き継ぎが切れている (口が無い)、 または段階 3 が要らない |
| `applied` | 抜粋に置き換えた (内訳 `counts`・忘却の記録の行 `forgetLines` / `forgetOmitted`・抜粋の字数) |
| `fallback` / `no-doc` | 履歴に中身が無く文書を作れない |
| `fallback` / `refine-failed` | 整理の前の判断の節の更新に失敗した (文書は機械的な節だけ書いた) |
| `fallback` / `not-smaller` | 抜粋に置き換えても減らない・落とすものが無い |

文書の保存の失敗・レート制限は今までどおり整理の失敗 (`task-handoff-failed`。 履歴は元のまま)。

### 9.7 前方一致

書き換えは整理イベントの 1 回 (`reduction:<ID>`) のまま。 新しい書き換えの理由は足していない。 ポインタは先頭のまま変えないので、 前方一致はポインタまで保つ。
抜粋はポインタの直後に置くので、 次の整理まではその後ろに足すだけ。

### 9.8 回帰テスト

  手動・規則 1 のどちらでも、 抜粋はいつも 1 件・ポインタは先頭・依頼の原文はそのまま・要約は 0 件・system は 1 件以下、 整理の後の P は 14.8K〜15.1K トークンで一定 (枠 131,072 の 2 割未満・幅 4,000 未満)。

## 10. リスク・未確認

- 判断の節の更新を本体と同じ並びで送るので、 スロットが 1 つのサーバでは、 その後の本体呼び出しが前回の本体の並びの位置へ戻れるかはサーバのチェックポイント次第 (混成モデル。 prompt-prefix-stability.md §2.2)。 実機の `tokensCached` で確かめる (未確認)
- 続きか別かの分類を誤って「別」 にすると、 続けたかった文脈が 1 行に畳まれる。 文書を `file_read` で読めば作業は続けられ、 畳む前の完全な履歴は保存したセッション (§5 の 4-2。 文書の `archivedSessionId`) を `/resume` すれば戻る。 誤りが多ければ印の語を増やす
- 依頼の原文に非常に長い貼り付けがあると文書が大きくなる (文脈には載らない。 第 2 段の抜粋は頭だけ)
- 第 2 段で落とした利用者の発言は、 抜粋の字数を越えた分は文書 (`file_read`) にしか無い。 決まり・制約に入っていない細かい指示は、 モデルが文書を読まない限り見えない (§9.2 で更新の指示を強めた)
- 第 2 段の抜粋の道では、 整理の前の判断の節の更新 (本体と同じ並び + 指示) が要約の呼び出しの代わりになる。 実機での所要時間と、 置き換えた後の `tokensCached` (ポインタまでしか一致しない) は未確認
- `/context` の「今 /compact した場合の見込み」 (`previewReduction`) は今も要約の道で数える (文書の抜粋の見込みは出さない)
