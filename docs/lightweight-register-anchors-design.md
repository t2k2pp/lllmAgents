## 1. 動機

### 1.1 じゃんけんセッションが露呈した「反対の尾」

`strategic-todo-design.md` は drawDot 事件 (弱モデルが 51 分思考ループして過小納品) がトラウマの起点で、設計全体が **「過小・計画蒸発を防ぐ」方向に重く倒れている**。じゃんけんセッションはその**反対の尾 (over-planning)** を露呈した:

- ユーザー依頼: 「セカンドLLMとじゃんけんをして、どっちが勝ったか教えて」 — 本来 `explore` (2-3 文で即答、成果物なし) で終わる軽量タスク
- 実際: メインエージェントの推論 **7 ターン** + セカンド呼び出し 1 = 計 8 回の生成。約 20 分
- 内訳の無駄:
  - turn 1 で**いきなり `todo_append`** (3 項目)。レジスター宣言テキストすら無し
  - turn 5/6/7 が「ToDo を 1 個ずつ completed にするだけ」で各々フル推論 1 回を消費
- 理想は 2-3 ターン。実測は **2 倍以上の冗長**

### 1.2 根本原因 — 「重さを見分ける判断材料」の片側欠落

当初の仮説「迷ったら重く倒す圧力が janken を standard に上げた」は**不正確**だった。ログ上モデルは重さを天秤にかけた形跡がゼロ (宣言テキストも出さず反射的に `todo_append`)。真因はユーザー指摘の通り:

> **レジスター判定木が「重い側のアンカー例」しか持たず、「軽い側のアンカー」が欠落している。**

`shared-principles.ts buildAcceptanceRules()` の具体例は全てコーディング寄り (「32x32 描画順」「node --check」)。「じゃんけん」「占い」「雑談」「一発回答」のような**軽い側のアンカーが一つも無い**。判別材料が片側しか無いモデルにとって、明らかな純粋質問以外は**全て「分類不能」**になり、デフォルト着地点が `todo_append` (後述 §1.3 の反射ドリル) になる。

そして「迷ったら必ず standard 以上に倒す」(`shared-principles.ts:52`) は、**軽重を見分けられるモデルには安全な保険だが、見分けられないモデルに渡すと「常に重く」に化ける**。判別材料が無い → 常に「迷っている」 → タイブレーカーのはずが**一律エスカレーション装置**になる。T3 (ローカル 27B) はまさに見分けられない側で、最も裏目に出る。

### 1.3 加担している 3 つの設計圧力 (現状コード)

| # | 圧力 | 場所 | 作用 |
|---|---|---|---|
| ① | レジスター判定が「分からなければ standard」「迷ったら必ず standard 以上」 | `shared-principles.ts:37,52` | 軽量タスクの逃げ道が無く standard に落ちる |
| ② | 「宣言だけで終わるな、同ターンで必ず `todo_append` か実装ツールを呼べ。さもなくば自己点検発動」 | `system-prompt.ts:141,147` | 書くファイルが無い軽量タスクでは `todo_append` が唯一の充足手段 → 防衛反射 |
| ③ | ToDo 過多検知が T3 で OFF、かつ新ツール (`todo_append`/`todo_mark`) を数えない | `capability-tier.ts:143` / `agent-loop.ts:1776` | 暴走を止めるガードレールが二重に無力 |

### 1.4 Claude Code との対比 (なぜあちらは過剰にならないか)

| 観点 | lllmAgents (現状) | Claude Code |
|---|---|---|
| 判定材料 | 重い側の例のみ | **両側の例。ツール定義に "When NOT to use" + trivial 例 (hello world, 単一編集, 質問) を内在** |
| 毎ターンのツール強制 | あり (計画蒸発の脅し) | なし (防衛反射が発生しない) |
| 不確実時の既定 | 重く倒す | 軽く / そのまま答える (ミニマリズム) |
| 過多抑制 | 反応的 nudge を後付け (T3 で OFF) | 基準をツール定義に内在化 (源流で抑制) |

**正直な但し書き**: Claude Code がこれで成立するのは、基準を宣言的に置いて「あとはモデルに委ねる」ことができる強いモデルだから。弱モデルに同じ宣言文だけ渡すと逆に過小プラン (drawDot の再来) に倒れるリスクがある。だから lllmAgents が「強制＋エスカレーション」で補おうとした動機自体は正しく、**補い方が裏目に出ただけ**。正しい折衷は §2 で述べる。

## 2. 設計原則

### 2.1 反応的検知ではなく proactive な判断材料 (源流修正)

`strategic-todo-design.md §3.4` は既に **「ヒューリスティック検出 → nudge は false positive が怖い。agent に状態表明の手段を提供して自己宣言させる」** を原則化している。本書はこれを軽量側にも対称適用する:

> **過剰プランを「検知して叱る」のではなく、「軽重を見分ける判断材料を最初から両側そろえる」ことで源流から抑える。**

これは §1.3 の③ (T3 で過多検知 OFF の理由 = 「scaffolding 増加が判断負荷を上げる」`capability-tier.ts:141`) とも整合する。弱モデルに反応的 nudge を足す方向は判断負荷を上げるだけで筋が悪い。判断材料を増やすのは負荷ではなく**ガイド**。

### 2.2 「軽重の両側アンカー」を判定木に対称配置

`strategic-todo-design §2.4` の「クリエイティブ自由 vs ハーネスガイド」線引きを踏襲。ハーネスは**「何を作るか」には口を出さず、「どこまでやれば終わりかの目安」だけを両側から例示**する:

| 軽い側 (新規追加) | 重い側 (既存) |
|---|---|
| じゃんけん / 占い / サイコロ / 雑談 | 32x32 描画 / マルチファイル実装 |
| 「どう思う?」「教えて」一発回答 | 「本番品質で」「テストまで」 |
| → ToDo もファイルも作らず即答 | → todo_append で 3-5 項目 commit |

弱モデルのために、**軽い側の負の例を Claude Code より多め・濃く**置く (§1.4 但し書きの折衷)。

### 2.3 「迷ったら重く」の適用範囲を限定する

「迷ったら standard 以上」は維持するが、**発火条件を「成果物を伴う実装依頼で粒度が曖昧なとき」に限定**する。会話・遊び・一発回答といった「そもそも成果物が無い」カテゴリには適用しない (= explore で確定)。これにより本ルールが本来の「稀なタイブレーカー」に戻る。

### 2.4 反射ドリルに explore の逃げ道を明記

②の「宣言だけで終わるな」原則 (`system-prompt.ts:147`) は維持しつつ、**「explore レジスターのときは何も呼ばず即答してよい (それは計画蒸発ではない)」** を明示的な例外として加える。これで「書くファイルが無い → 仕方なく todo を掴む」防衛反射を断つ。

## 3. 仕様

### 3.1 レジスター判定木に軽量アンカーを追加 (`shared-principles.ts buildRegisterRules`)

> **決定 (2026-06-07, レビュー済)**: 新レジスター `chat` を**新設せず**、既存 `explore` を「**成果物を作らない即答全般 (会話・遊び・一発回答 + 調査回答)**」に**意味拡張**する。理由は Claude Code 準拠 — Claude Code はレジスター分類自体を持たず、「成果物が無いものは簡潔に即答」という単一バケツで扱う。段階数を 4 に保つことで弱モデルの分類負荷を増やさない (§1.4 の精神)。「じゃんけん」と「比較して」は同じ explore の 2 サブケースとして判定木に並べる。

**T3 版** (`shared-principles.ts:31-37`) を以下に改修:

```
# レジスター判定 [必須・テンプレ厳守]
ユーザー依頼をまず 4 種に分類 (上から順に判定、最初に当たったもの):
- (a) 成果物を作らない依頼 → explore: ファイルも ToDo も作らず即答。2 つの形がある:
      ・会話・遊び・一発回答 (じゃんけん/占い/サイコロ/挨拶/雑談) → そのまま 1-3 文で答える
      ・調べて答える質問 ("どう思う?" "どんな選択肢?" "比較して") → 短く調査して答える
- (b) 「ラフに」「とりあえず」 → rough: 最小実装 + 構文チェックのみ
- (c) 通常の実装依頼 → standard: 計画 → 実装 → 動作確認まで
- (d) 「本番品質」「テストまで」 → production: テスト + ドキュメント整合

迷うのは (c) か (d) のときだけ。そのときは重い方 (d) に倒す。
(a) は迷う対象ではない — 成果物が無いものは即答 (todo_append すら不要)。
```

ポイント:
- **explore を「成果物なしの即答全般」に拡張**。会話・遊びを (a) のサブケースとして明示 (段階数は 4 のまま)
- 「迷ったら重く」を **(c)/(d) 間だけに限定** (§2.3)
- T2 版の表の `explore` 行に「会話・遊び・一発回答も含む。ファイルも ToDo も作らない」を追記。`shared-principles.ts:52` の「迷ったら production 寄り」に「ただし成果物を伴う依頼に限る」と但し書き
- T1 版は 1 行追記のみ (「会話・遊び・即答系は explore でそのまま答える」) — 強モデルは過剰説明不要

### 3.2 反射ドリルに explore 例外を明記 (`system-prompt.ts`)

`system-prompt.ts:147` の「宣言だけで終わらせない」原則に例外行を追加:

```
**例外**: explore レジスター (会話・遊び・一発回答・調査回答) では、ツールを一切
呼ばず 1-3 文のテキストで即答してよい。これは「計画蒸発」ではない (成果物が無い
タスクの正しい完了形)。「じゃんけんしよう」に todo_append を作るのは過剰。そのまま
答えること。
```

`system-prompt.ts:141` の「promise だけで終わらせない」にも同趣旨の but 節を 1 つ。

### 3.3 ToDo ツール定義に「使わない基準」を内在化 (`todo_append` description) — **最重視ピース**

> **決定 (2026-06-07)**: Claude Code の実証では、軽重制御の本丸は**レジスター分類ではなくツールレベルのゲート** (TodoWrite の "When NOT to use") にある。tool description は呼び出し直前に必ずモデルの目に入るため、判定木より effect が強い。本書もこれを Phase 1 の**最重視ピース**に格上げする。

Claude Code 流に、`todo_append` のツール description へ **"When NOT to use"** を追記:

```
[使わない場面]
- 1-2 ステップで終わる軽量タスク
- 会話・遊び・質問への一発回答 (じゃんけん/占い/"どう思う?")
- ファイルも検証も伴わないタスク
これらに todo を作るのは過剰。そのまま実行/即答する。
```

これは §2.1 の「判断材料を源流に置く」の中核。tool description は毎回モデルの目に入るので、判定木より効きやすい。

### 3.4 過多検知を「新ツール対応 + ソフト発火」に補修 (任意、Phase 2)

§1.3③ の通り現 `maybeWarnPlanTodoOveruse` は `todo_write` しか数えず無力。ただし §2.1 の方針上、**反応的 nudge は最後の保険**に格下げする:

- `todo_append`/`todo_mark` の呼び出し回数もカウント対象に追加 (`agent-loop.ts:1776`)
- 閾値を「軽量タスク (response_complete までの総ターンが少ない見込み) で todo が連続」に寄せる
- T3 では **依然 OFF をデフォルト** とする (§2.1)。源流修正 (§3.1-3.3) で十分かを試金石で先に検証し、足りなければ初めて検討
- 発火しても叱責調を避け、「この規模なら todo 無しで直接進めて良い」と**選択肢提示**に留める

> Phase 1 (§3.1-3.3) の源流修正だけで janken が 2-3 ターンに収まるなら、§3.4 は不要。**まず source を直し、検知は入れない**のが §2.1 の精神。

## 5. 評価 — 何を持って「成功」とするか

### Phase 1 完了基準

1. **再現テスト (janken)**: Qwen3.6-27B で「セカンドLLMとじゃんけんして勝敗を教えて」を再走 →
   - `todo_append` が呼ばれない (または 0 回)
   - 総ターン数が **3 以下** (現状 7)
   - レジスターが chat/explore と自覚されている (ログ確認)
2. **過小側の非回帰 (最重要)**: drawDot 試金石 (32px ウサギ, standard/production) を再走させ、**chat 追加で実装タスクが手抜きにならない**ことを確認。「実装依頼なのに chat で即答して終了」が起きないこと
3. **境界ケース**: 「電卓アプリ作って」(standard) / 「サイコロ振って」(chat) / 「この設計どう思う?」(explore) の 3 件で正しくレジスター分類されること
4. **回帰ゼロ**: 既存 vitest 全件 pass

### 言語化されるべき結論

Phase 1 完了時、**「源流に判断材料を両側そろえるだけで、弱モデルの過剰プランは止まるか」**を実証データで判断する。`strategic-todo-design.md` (過小側) と本書 (過剰側) の対で、**ハーネスが両尾を判断材料で抑えられる**ことを示せれば、「強制と検知に頼らず、ガイドで弱モデルを正しく振る舞わせる」設計思想が validated される。

### 振動による最適化という前提

本書は「強める/弱める」の振動で最適点を探る一手であり、最終形ではない。`strategic-todo-design` で重く倒した反作用を、ここで軽く戻す。次の試金石で行き過ぎ (過小再発) が見えれば、また少し重く戻す。**学習と忘却のアニーリング**として、各調整は設計書に履歴を残し、どちらへ何故倒したかを追跡可能にする。
