## 1. 結論サマリ

| 論点 | 結論 |
|---|---|
| **50 → 100 への引き上げは必要だったか?** | **必要だった**。 50 で打ち切られた user span が 4 件、 100 にして初めて完走したのが 1 件 (82 反復) ある。 50 は実運用で常時不足。 |
| **100 で十分か?** | **当面は十分**。 観測した最大反復は 82。 ただし「行動が効率的なら 50 でも収まったはず」 の事象が複数。 100 は安全側設定であり、 上限値そのものより **反復を浪費させる行動パターン** が本丸。 |
| **本質課題は何か?** | (A) 同じ引数での失敗リトライが検知されない (B) 大ファイルの再読込み連打 (C) 計画の蒸発と作業の二重実行 (D) ビルド/起動サイクルの粒度過大。 |

## 3. 高反復スパンの実態 — 何が浪費されていたか

### 3.1 50 反復スパン #1: 「APPLとかうまく取れてない」 (15-15, T34→T84)
- bash 26, file_edit 20, web_fetch 2, file_read 2。
- 株価データ取得ロジック修正 → npm 検証 → 再修正のサイクル。 同一の `npm run verify` 実行 5 回、 build 6 回が混在。
- 各検証で全件再収集を試みていた可能性 → **「失敗箇所だけ追検証する手段の欠如」** が反復を増やしている。

### 3.2 50 反復スパン #3: 「ダッシュボード UX 改善」 (15-15, T286→T336)
- `enter_plan_mode → file_read×5 → exit_plan_mode → file_write×3 → file_edit×19` の流れ。
- 19 連発の `file_edit` は **同一ファイルへの 5–10 行単位の小パッチが大半** であり、 1 回の `file_write` で全体置換した方が反復数も検証コストも小さかった。

### 3.3 50 反復スパン #4: 「画面確認」 (15-15, T359→T409)
- bash 15, browser_click 8, browser_snapshot 6, vision_analyze 3。
- ブラウザ操作の **試行錯誤クリック → snapshot → 再クリック** のループ。 各 snapshot は引数同一の `{}` で副作用がないにも関わらず毎ターン取得。
- DOM が変わらない限り snapshot キャッシュを再利用すれば 4–6 反復削減可能。

### 3.4 82 反復スパン: 「複数選択 → 比較グラフ」 (05-06, T38→T120) — 最重要事例

最も豊富な失敗パターンが詰まったスパン。 タイムラインから抜粋:

| Turn | Tool | 結果 | コメント |
|---:|---|---|---|
| T44–T49 | file_edit ×6 (app.js) | ✓ | UI追加に必要な 6 箇所を逐次パッチ |
| **T50** | file_edit (renderHeatmapTile) | **✗** | 「old_string found 2 times」 |
| T51 | grep | ✓ | 重複箇所確認 |
| T52 | file_read | ✓ | app.js 再読込 |
| **T53** | file_edit (同一引数) | **✗** | **同じ old_string で同じエラー** |
| **T54** | file_edit (別箇所だが同様) | **✗** | また「found 2 times」 |
| T55–T56 | file_edit | ✓ | ようやく一意化して成功 |
| ... | | | 多数の file_edit / file_read |
| **T79** | bash node --check | **✗** | 構文エラー発覚 |
| T82 | bash python heredoc | ✓ | 状態確認 |
| **T83** | bash node --check | **✗** | まだエラー |
| T84 | file_read app.js | ✓ | 再々読込 |
| T85 | bash git diff | ✓ | 差分確認 |
| **T86** | bash git checkout -- | **✗** | **rollback 試行が失敗** (untracked 等) |
| T87–T91 | bash / read で復旧 | ✓ | 何とか動く状態に戻す |
| **T92–T97** | file_edit ×6 (app.js) | ✓ | **T44–T49 とほぼ同じ編集を最初からやり直し** |
| **T98** | file_edit (renderHeatmapTile) | **✗** | **T50/T53 と同じエラーが再発** |
| T99–T100 | grep / read | ✓ | 二度目の調査 |

ここから読める病理:
1. **「old_string found 2 times」 は対処法（`replace_all=true` か一意化）が明示されているのに、 同じ引数で 3 回再試行**。 ツール失敗メッセージが学習に使われていない。
2. **構文エラー時の rollback シーケンスが脆弱**。 `git checkout` で戻そうとして失敗 → 結果として T44–T49 と同等の編集を T92–T97 で再実行。 これだけで 6 反復の純粋な再作業。
3. **再作業中に T50 と同じ重複文字列バグも再発** (T98) → 同じ轍を 1 セッション内で 2 度踏む。

このスパンは **効率的に進めれば 30–40 反復程度に収まったはず**。 「100 必要」 と「50 で十分だった」 が同居している典型例。

## 4. 設計提言

「上限緩和」 と「行動の品質改善」 を分けて提案する。

### 4.1 反復上限値そのもの

| 提案 | 理由 |
|---|---|
| **`MAX_TOOL_ITERATIONS = 100` を当面維持** | 観測実績の max が 82。 50 では 9% の発話で打ち切り発生という事実 (定量) を尊重。 |
| **将来的にはモデル/レジスター別に可変化** | `production`/`standard`/`rough`/`explore` で切る (内部設計書 §1 に既存)。 例: explore=20, rough=30, standard=80, production=150。 上限が上がる前に「効率化」 が機能する設計に倒す。 |
| **打ち切り時の挙動を改善** | 現状は黄色ログを出して return。 自動で「進捗サマリと残作業をユーザーに提示しつつ続行可否を ask_user で確認」 すれば、 上限に張り付く 9% でも作業継続できる。 |

### 4.2 同一引数リトライの検出強化（最重要）

`agent-loop.ts:601-622` の `MAX_REPEAT_TOOL=3` は **直前ターンとの一致** しか見ていない。 T50/T53/T98 のように間に grep/read を挟まれると無効化される。

提案: スライディングウィンドウ + 失敗連動の検出に変える。
- **直近 N=10 ターン以内に同一 (toolName, arguments) の失敗が 2 回出たら強制中断 / 別アプローチ要求**。
- 失敗時の `error` 文字列が同一の場合はさらに重く扱う (`old_string found N times` などはツール側からの明示的助言なので、 LLM への self-check 注入で「エラーの指示通り対応せよ」 と強制リプロンプトする)。

擬似コード（agent-loop.ts に追記）:
```ts
const recentFailures = new Map<string, {turns: number[], lastErr: string}>();
// ツール失敗時:
const sig = `${toolName}:${arguments}`;
const rec = recentFailures.get(sig) ?? {turns: [], lastErr: ""};
rec.turns.push(iteration);
rec.turns = rec.turns.filter(t => iteration - t <= 10);
if (rec.turns.length >= 2 && rec.lastErr === errMsg) {
  // 直近10反復内に同じ引数+同じエラーで 2 回失敗 → 強制 self-check 注入
  injectSelfCheck("同じ引数+同じエラーが続いています。エラー文 'X' の指示に従って引数を変えるか、別ツール（grep/file_write 等）に切り替えてください。");
}
rec.lastErr = errMsg;
recentFailures.set(sig, rec);
```

### 4.3 大ファイル再読込みの抑制

15-15 セッションで `app.js` を 22 回読み直し。 `file_edit` 直後に `file_read` を入れる行動が頻出していた（Edit ツールが既にファイル状態を更新しているのに）。

提案:
- **`file_edit` 成功時のレスポンスに「現在の関連箇所 ±20 行」 を含める** → 直後の re-read を不要にする。 ツール側のレスポンス整形で実装可能。
- システムプロンプトに **「file_edit 直後の file_read は禁止 (Edit が成功していればファイルは更新済み)」** を明記。
- file_read のキャッシュ: 同一ファイルを「最後の編集後に既に読んだ」 状態なら、 LLM 向けレスポンスは「キャッシュ済み: 前回読込時から差分なし」 と短く返す。

### 4.4 ビルド/起動サイクルのコスト

`npm run build && PORT=3310 ...` を 11 回繰り返し（15-15）。 1 回 30s〜2min かかる重いコマンドを編集ごとに走らせている。

提案:
- システムプロンプトに **「複数 edit 後にまとめて build 1 回。 1 edit ごとの build/run 禁止」** を追加。
- `bash` ツールに簡易な **時間累積警告**: 同一セッションでの累積 bash 実行時間が N 分超えたら自己点検注入 (「重い検証を頻発しています。差分検証や node --check で軽くできませんか?」)。

### 4.5 ブラウザ操作の冗長性

`browser_snapshot {}` を 19 回連発。 同一 DOM の場合、 直前と差分なしなら短縮レスポンスにすべき。

提案:
- snapshot ハッシュをキャッシュ。 直前と同一なら「変化なし (前回参照)」 のみ返す。
- `browser_click` 直後の `browser_snapshot` は自動連動 → 個別に LLM が呼ばなくて済む API 設計を検討。

### 4.6 計画モード突入の制限

15-15 セッションで `enter_plan_mode` 4 回。 plan を立てては抜け、 また立てる「計画蒸発」 の典型。

提案:
- 同一 user span 内の `enter_plan_mode` を **2 回まで**。 3 回目は強制的に「既存 todo を見直してから判断」 のメッセージに置換。
- `todo_write` も 1 user span あたり上限を設ける（例: 5 回）。 細切れの todo 更新で反復が嵩む。

### 4.7 自動 rollback の安全化

T86 の `git checkout -- public/app.js` 失敗で復旧フローが破綻。

提案:
- `bash` で `git checkout`/`git reset --hard`/`rm -rf` を実行する前に、 直前で **作業ファイル一覧を `git status --short` でスナップショット取得を必須化** (システムプロンプト + 必要ならツール側ガード)。
- 別案: 編集セッション開始時に `git stash --include-untracked` で安全網を張る。 内部設計書の編集セッション機能（あれば）に統合。

### 4.8 コンテキスト圧縮閾値の前倒し

平均 95K (200K の 47%) でも、 ピークは 172K (86%) で閾値 80% を超えてから圧縮発火。 圧縮中は LLM 呼び出しがブロックされ、 ストリーミング体験も劣化する。

提案:
- 閾値を **0.65–0.7 に前倒し**。 圧縮頻度は上がるが、 1 回の圧縮対象が小さくなり遅延も小さい。
- 大きな tool_result (>10KB) は履歴に残す段階で **要約済み (要点 + 全文の先頭 N 行) で保存**。 web_fetch で 30KB 取得が 2 連発した事例 (15-15 T40, T48) があり、 こうした応答は元のまま履歴に残す価値が低い。

## 6. 観測指標としての提案

「効率改善が効いているか」 を継続観測するために、 ログ集約で次を可視化したい:

- user span あたりの反復数の中央値 / p90
- 同一 (toolName, arguments) の重複呼び出し率
- 同一ファイルの re-read 数
- bash 累積実行時間 / セッション
- 反復上限 (MAX_TOOL_ITERATIONS) への到達率

これらをセッションログに集計するスクリプト (例: `scripts/analyze-loop.mjs`) を作るのは別タスクで切り出し可能。

## 7. 補足: MAX_TOOL_ITERATIONS=100 引き上げの位置づけ

「50 で運用していたら 9% の発話で打ち切られていた」 という事実が、 引き上げの正当性を支える。 一方で、 観測されたスパンの多くは「効率的に進めれば 50 以下で済んだ」 余地を含む。 つまり:

- **100 は対症療法として正しい**。 緊急で必要だった処方。
- **本質治療は 4.2〜4.4**。 これらが効けば、 100 という数字は「事故時の上限」 として機能し、 実運用では 50 内に大半が収まるようになる。
- **将来的には可変化 (4.1)**。 production レジスターのみ高い上限、 rough/explore は低めにすることで、 LLM に「タスク粒度に応じた切り上げ」 を意識させる副次効果も期待できる。

設計タスクに着手する際は、 P0 (4.2 + 4.3) を 1 PR で出し、 効果を計測してから P1 以降に進める段階リリースを推奨。
