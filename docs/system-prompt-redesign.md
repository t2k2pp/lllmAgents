# システムプロンプト再構成 (2026-06)

## 背景・動機

複数の開発セッションで `src/agent/system-prompt.ts` と `src/agent/shared-principles.ts` に
行動原則を継ぎ足し続けた結果、システムプロンプトが肥大・破綻した。`/context` でベースライン
消費を確認したユーザーから「何もしていないのに大きい」「誰向けか不明な注記が混入している」
「常駐すべきでないものが居座っている」という指摘を受け、独立サブエージェントによる批判的
レビューを実施。本書はその診断と再構成方針を記録する。

### 実測（再構成前）

`buildSystemPrompt()` は内部で project指示・memory・rules を読み込むため、full には作業環境
依存の可変分が含まれる。**今回の編集対象はコアアイデンティティ + `shared-principles.ts` の
8 builder = 「# 環境」より前の "behavioral" セクション**。env/project/memory/rules は本タスクの
スコープ外。

| Tier | full | **behavioral (編集対象)** | rest (env/project/memory/rules, スコープ外) |
|---|---|---|---|
| T1 (Claude/GPT-5 級) | 3,414 | **1,092** | 2,323 |
| **T2 (デフォルト)** | 6,679 | **4,356** | 2,323 |
| T3 (7B 級) | 3,823 | **1,960** | 1,863 |

**構造的欠陥**: 編集対象の behavioral が T2=4,356 と、弱モデル向け T3=1,960 の約 2.2 倍、
T1=1,092 の約 4 倍に肥大。「T2 は賢いから全部渡してよい」という逆さまの前提で膨らんでいた。
本来 T2 こそ段階的開示 (tool-guides の遅延注入) を最も活用すべき層である。

> 注: ツール description は毎ターン `tools` 配列として常にモデルへ送られる (= 常駐相当)。
> よって常駐ブロックを「既に description が説明している内容」へ委譲すると、二重送信が解消され
> 実際にトークンが減る (description 側は元から送られているため増分ゼロ)。

## 設計思想

1. **コアは「原則1行ずつ」に圧縮する。** 「何を・なぜ」だけを常駐させ、「どうやって (how)」の
   詳細は既存の段階的開示機構 (`tool-guides.ts` のツール初回注入) へ寄せる。
2. **常駐に残すのは2種だけ**:
   - (a) タスク全体の判断軸 = レジスター4段階の定義表
   - (b) ツールを呼ぶ前に知らねば手遅れになる安全則 = 「同一ツール×同一引数で2回失敗→別手」
3. **how 詳細は遅延注入**: 検証ルール表・委任の4点・ツール別エラー復旧例などは、該当ツールを
   実際に使う瞬間に注入する (既に機構あり、使い切れていなかった)。
4. **tier 設計自体は維持**。ただし T2 を「段階的開示を最も活用する層」へ反転させる。
5. **削った内容を消失させない**。常駐から外すものは必ず注入ガイド/ツール description へ移設し、
   カバレッジを確認してから常駐を削除する。

## 診断（レビュー確定事項）

### A. 漏れた開発者メモ（モデルに無意味なノイズ／常時混入）
- `shared-principles.ts:91` T2: 見出し `## ツール (旧 \`todo_write\` は deprecated)` —
  モデルは todo_write を知らないため deprecated 注記は純ノイズ。→ `## ツール` へ。
- `shared-principles.ts:81` T3: 末尾行 `旧 \`todo_write\` は deprecated — ...`。→ 削除。
- `shared-principles.ts:155` T2: `(観測ログで同一 build を 11 連発した事例あり)` という
  設計者の観察メモ。→ 削除 (検証圧縮で消える)。

補足: `tool-guides.ts:146` の `todo_write` few-shot は「todo_write を実際に呼んだ時だけ」
反応注入されるため、deprecated 言及は文脈的に妥当 (常駐の漏れとは別物)。今回は手を入れない。

### B. 冗長／重複（同一 T2 プロンプト内）
| 概念 | 重複箇所 | 対処 |
|---|---|---|
| explore は即答してよい | 5回 | コア行動原則に1回集約、他を削除 |
| 計画蒸発の禁止 | 3回 | コア+acceptance の2→1へ削減 |
| edit 直後の re-read 禁止 | 複数 | `buildToolUsageRules` に一本化 (現状維持) |
| レジスター宣言の手順 | 2回 (コア詳述 + buildRegisterRules) | コアは1行化し buildRegisterRules へ委譲 |

### C. 段階的開示の自己矛盾
- **検証 (最重要)**: `buildVerificationRules("T2")` は冒頭で「詳細は bash/file_write 初回注入で
  来る (段階的開示)」と宣言しつつ、直後に14行の詳細を返す。`tool-guides.ts` の `verification`
  ガイド (全 tier に bash/file_write 初回注入) と二重。→ 常駐は原則2行に圧縮。
- **検証粒度 (細切れ build 禁止/PID 放置禁止)**: 注入ガイド側に存在しない。→ 常駐から外す前に
  `verification` ガイドへ移設する。
- **応答完了**: `system-prompt.ts:158-163` の6行は `response_complete` の description が既に
  説明済み (自己点検 N/3、Acceptance ゲート)。→ 常駐は2行へ圧縮。

- `buildAcceptanceRules` T2: 見出し `## ツール (旧 todo_write は deprecated)` → `## ツール`。

  プロセスは用済みで kill)」を追記 (常駐から移設、消失防止)。

### `src/tools/definitions/response-complete.ts`
- description 内の `todo_write` 表記を `todo_append` へ (deprecated 整合)。
- 応答完了の常駐圧縮にあたり「単純な挨拶・短い質問でも会話が完結したら呼んでよい」の一文は
  常駐側に短く残す (description には無く、explore 完了形の明示として有用)。

> **実装上の atomic 制約 (設計レビュー指摘)**: `buildVerificationRules` から「細切れ build/PID」を
> 削除する変更と、`tool-guides.ts` の `verification` ガイドへの追記は **同一コミットで** 行う。
> 分割すると移設漏れ＝足場消失のリスク。

## 残す足場（削ってはいけない／レビュー合意）
1. レジスター4段階の**定義表** (粒度判定の基準。T1 の1行要約には戻さない)
2. 「同一ツール×同一引数で2回失敗→別アプローチ」(ループ防止。ツール呼出前に必要なので遅延注入では遅い)
3. `buildCreativeRhythmRules` の「まず手を動かす→確認→次」(3行、弱モデルの発散予防)
4. 環境情報セクション全項目 (自己ポジション把握)
5. T3 の few-shot / failure-guide 注入機構 (正しい段階的開示。弱モデルの本当の足場)

## 目標（実測に基づき再設定）
- **主目的は質**: 漏れた開発者メモの除去 / 重複の統合 / 段階的開示の自己矛盾解消。
- **副次目標 (量)**: T2 behavioral 4,356 → **~3,600 tok 前後 (約15-18%減)**。当初の「40%減」は
  full 値 (project/memory/rules 込み) を誤って基準にした過大目標だったため撤回 (設計レビュー指摘)。
  スコープ内で削れるのは ~600-700 tok が現実的。
- 削減後も上記「残す足場」は全て保持。移設先カバレッジを実装時に確認。
- 実装後に behavioral / full を再実測し、本書の数値を更新する。

## 実装結果 (実測)

| Tier | behavioral 前 → 後 | full 前 → 後 |
|---|---|---|
| T1 | 1,092 → 1,092 (±0、対象外) | 3,414 → 3,414 |
| **T2** | **4,356 → 3,511 (-845, -19.4%)** | 6,679 → 5,834 (-12.6%) |
| T3 | 1,960 → 1,937 (-23) | 3,823 → 3,800 |

主目的 (漏れメモ除去 / 重複統合 / 検証の自己矛盾解消) を達成し、副次目標の behavioral
~15-18% 減も上回る -19.4% を実現。tool-guides の `verification` ガイドは +約80 tok 増えたが、
これは bash/file_write 初回使用時のみ注入される非常駐分。

### 第2パス (2026-06-08、「脂肪→筋肉」) — T2 をさらに圧縮
判断軸: 常駐すべきは「何をするか」と非自明な安全則だけ。脂肪=(1)理由・正当化 (人間向け説明)、
(2)ツールIO・シグネチャ (body.tools の description で毎ターン送信済み)、(3)他節との重複、(4)動機づけ散文。
- レジスター: 「暗黙合意/これが無いと…」理由と粒度判定3項目を削除→表+1行。**(b)-(d) 漏れ参照バグ**も除去
- 戦略ToDo: 効能3点・todo_*シグネチャ例 (description と二重) を削除→1段落
- 応答完了: 自己点検の機構説明 (description と二重) を削除
- ツール原則: file_edit 復旧例をエスカレーション節へ一本化 (重複解消)
- 想定外信号: 締めの心構え散文を削除、4手順を1段落に
- 仕様ファイル: 3項目→1段落
- 委任: ユーザー指摘の「分かりづらさ」を是正し task/second_llm_agent/second_llm_consult を1行ずつ明確化 (clarity優先で +α)

実測: **T2 behavioral 3,511 → 2,689 tok (-822, 累計 4,356→2,689 = -38%)**。T1/T3 は対象外。
当初の -35% 目標相当に到達 (full 基準)。委任の明確化でトークンを一部戻したが質を優先。

### 第2パス追補 — 全節を素の日本語へ (ジャーゴン/スラング一掃)
「指摘箇所だけ直す＝それ自体がパッチ対応」というユーザー指摘を受け、冒頭だけでなく**全15節を通しで**見直し:
- 英語語の直訳混入を排除: commit→書き出す / head→頭 / fallback→勝手な代替 / return→呼び出し元に返す /
  インライン処理→自分で処理 / ctx→文脈 / Acceptance Checklist・Criteria→完了条件(リスト)
- 内輪スラングを排除: 壁ドンループ→同じところで詰まっている / 沼の入口→(削除) / 回帰→壊れたら前の版に戻す
- 見出しも平易化: 創造的反復のリズム→作りながら進める / 失敗時のエスカレーション→同じ失敗を繰り返さない /
  想定外の信号への基本姿勢→想定外が起きたときの姿勢
- response-complete.ts の facing 文字列も「完了条件」へ揃えた (prompt と用語統一)
- 実測 T2 behavioral ≈ 2,596 tok (累計 4,356→約2,596 = 約-40%)

### 「レジスター」→「完了レベル」へ改名 (ユーザー判断: 完了レベル)
言語学の借用語「レジスター」はローカルLLMにも不透明 (ユーザー「私にピンと来ない言葉がモデルに来るのか?」)。
「完了レベル」へ改名。**当初『code 変更を伴う』と述べたのは誤りで、訂正**: agent-loop のパーサ
(`detectRegisterFromText`) は「このタスクは」+ レベル名 (explore/rough/standard/production と日本語変種) で
判定しており、「レジスター」という単語は見ていない。よって改名はプロンプトのみで安全。
- system-prompt.ts / shared-principles.ts の「レジスター」を全て「完了レベル」に。見出し「対話レジスター」→「完了レベル」
- 段階名 (explore/rough/standard/production) は英語のまま (ユーザー選択)
- agent-loop の soft-cap 表示メッセージ2箇所も「完了レベル」へ統一 (表示のみ、解析非依存)
- パーサに「完了レベル[:：]」トリガを追加 (モデルが新用語を echo しても拾えるよう堅牢化)。
  宣言文 "このタスクは standard として進めます" は置換後も同一で従来通り検出 (regex 直接検証済)。

## 検証
- 変更前後で T1/T2/T3 のトークンを実測 (使い捨て tsx で `buildSystemPrompt` を直接レンダ)。済。
- `npx vitest run`: 変更ファイル領域 (tests/agent 183件) 全グリーン。既存の失敗5件は browser/security の
  Windows 環境依存 (unix socket / macOS 固有ロジック / /home パス) で、本変更前から失敗しており無関係
  (git stash で base 確認済)。

  - 設計者: 条件付き GO。トークン目標過大 (40%→実測ベースに再設定) / escalation の file_edit 例は

    復活 (ツールではなくハーネスメッセージへの反応なので遅延注入不可、description 再読依存より堅牢)。
