> **ステータス**: 2026-08-13 設計 / 実装
> **関連**: `docs/context-intelligence.md` (圧縮の既存設計) / `docs/ephemeral-context-design.md`
> (span 境界の揮発) / `docs/context-strategy.md` (後続。 圧縮・忘却・Clear の使い分け)

---

## 1. 背景

### 1.1 現状: 圧縮しかない

コンテキストが閾値を超えたときの縮約手段は **`HierarchicalCompressor` による要約圧縮 1 種類**のみ。

```
[古いメッセージ 40 件] ──要約──> [system: 「過去の文脈（圧縮）」 800 トークン]
[直近 10 件] ────────────────────> そのまま
```

境界より古いものは **一律に要約**される。 中身が何であれ同じ扱いになる。

### 1.2 圧縮の弱点

| 問題 | 具体例 |
|------|--------|
| **一律性** | 「絶対に忘れてはいけないユーザー指示」 も「もう用済みの `file_read` 結果 8,000 トークン」 も、 同じ要約器に入って同じ圧縮率で潰される |
| **不可逆な劣化** | ファイルパス・関数名・行番号は要約で丸められやすい。 プロンプトで「省略するな」 と書いても、 モデルは要約タスクだと思うと丸める |
| **要約自体が高コスト** | 40 件を 4 ブロックに分けて LLM 呼び出し 4〜5 回。 数十秒かかる。 その間ユーザーは待つ |
| **再取得可能性を考慮しない** | `file_read` の結果は **もう一度読めば手に入る**。 要約して劣化させるより、 捨てて「必要なら読み直す」 方が情報として正確 |

### 1.3 忘却という別解

**「何を覚え、 何を忘れるか」 をモデル自身に選ばせる**。

- 要約しない = 残すものは **原文のまま無劣化**
- 捨てるものは **完全に捨てる** (中途半端な要約を残さない)
- 捨てた事実は **必ず記録に残す** (何を捨てたか分からない状態を作らない)

圧縮の代替ではなく **第 2 の手段**として置く。 両者は得意な状況が違う (§7)。

## 2. 中心概念: セグメント

### 2.1 なぜメッセージ単位ではだめか

OpenAI 互換 API では、 `tool_calls` を持つ assistant メッセージと、 対応する
`role: "tool"` の結果は **必ずペアで存在**しなければならない。 片方だけ消すと 400 になる
(既存 `replaceOlderMessages()` が境界を前方にずらしているのも同じ理由)。

そこでメッセージではなく **セグメント (atomic に扱う塊)** を忘却の単位にする。

### 2.2 セグメントの定義

```ts
type SegmentKind = "user" | "assistant_text" | "tool_batch" | "system_note";

interface Segment {
  /** 履歴内の 1 始まり通し番号。 モデルはこの番号で忘却対象を指す */
  index: number;
  kind: SegmentKind;
  /** このセグメントに含まれる messages の [開始, 終了) */
  range: [number, number];
  /** 推定トークン数 */
  tokens: number;
  /** 1 行ダイジェスト (manifest 表示用) */
  digest: string;
  /** tool_batch のときの内訳: 呼ばれたツール名 */
  toolNames?: string[];
  /** 保護されているか (直近 N セグメント / 忘却済みトゥームストーン) */
  protected: boolean;
}
```

グルーピング規則:

| 入力 | セグメント |
|------|-----------|
| `user` メッセージ 1 件 | `user` セグメント 1 個 |
| `assistant` (tool_calls なし) | `assistant_text` セグメント 1 個 |
| `assistant` (tool_calls あり) + 続く `tool` 結果すべて | **`tool_batch` セグメント 1 個** (不可分) |
| 圧縮要約 / 忘却トゥームストーンの `system` | `system_note` セグメント 1 個 (**常に保護**) |

これで tool ペアの分断が構造的に起こり得なくなる。

## 3. 忘却の 3 アクション

セグメントごとにモデルが選ぶ。

| アクション | 意味 | 主な対象 |
|-----------|------|---------|
| `keep` | そのまま残す (既定) | ユーザー指示・未解決の判断・直近の作業文脈 |
| `thin` | **形は残して中身だけ落とす** | 巨大な `file_read` / `bash` 出力。 「何をしたか」 は残り「結果の本文」 が消える |
| `drop` | セグメントごと消す | 用済みの探索・失敗した試行・雑談 |

### 3.1 `thin` の具体的な変換

`tool_batch` に対して:

```
変換前:
  assistant: (tool_calls: file_read {path: "src/agent/agent-loop.ts"})
  tool:      <3,300 行のソース = 約 41,000 トークン>

変換後:
  assistant: (tool_calls: file_read {path: "src/agent/agent-loop.ts"})
  tool:      [忘却済み] file_read src/agent/agent-loop.ts の結果 (約 41,000 トークン) は
             履歴から削除しました。 必要なら再度 file_read してください。
```

**tool_call は残す**のがポイント。 消してしまうと「このファイルを読んだ」 という
行動の記録まで失われ、 同じファイルを何度も読み直す壁ドンループを誘発する。

ただし **tool_call 引数の本文は落とす**。 `file_write` の `content` や `file_edit` の
`old_string` / `new_string` など、 文字列引数のうち `file_path` / `path` / `url` 以外で
200 文字を超えるものは先頭 200 文字 + `[忘却済み]` 注記に切り詰める (JSON として読めない引数は触らない)。
書込中心のセッションではコンテキストの大半が引数側に乗るため、 結果本文だけ落としても減らない。

> 2026-10-17 myppt セッション (392 msg / 約 159K) で `contextReduction=forget` が
> 「実質削減が -85 トークン」 で不成立になった。 未保護 158 セグメント中 80 が thin しても 0 削減
> (結果は thin 済み、 残りは引数 82.7K)。 マニフェストは引数込みの total を出すため、
> モデルは大きく見える thin 済みの `file_write` を選び、 トゥームストーン分だけ増えていた。

thin 済みの結果・引数 (`[忘却済み]` を含むもの) は再変換しない。 各セグメントは
`thinGain` (thin で実際に減る量) を持ち、 0 のセグメントは
マニフェストで `thin済` と表示し、 thin 指定されても検証で無視する (§4.3)。
決定論版の forget-thinking も `thinGain` が 0 の batch は選ばない
(選ぶと「約 0 トークン削除」 の空振り記録だけがトゥームストーンに積もる)。

`assistant_text` および `user` に対する `thin` は先頭 200 文字 + 省略注記に切り詰める。
`user` の thin は「モデルが drop を選んだが格下げされた」 経路で必ず発生する (§4.3)。

### 3.2 なぜ `thin` を用意するか

実測上、 長時間セッションのコンテキストの大半は **ツール結果の本文**が占める。
そこだけ落とせば、 会話の筋 (ユーザー指示 → 何をした → どうなった) を
**一切劣化させずに** 大きく削れる。 圧縮ではこの分離ができない。

## 4. 忘却フロー

```
1. shouldReduce() が true (閾値超過) または /forget が呼ばれた
2. buildSegments(history) でセグメント化
3. 直近 keepRecentSegments 個 + system_note を protected にする
4. buildManifest() でモデルに見せる一覧を作る
5. LLM に「どれを keep / thin / drop するか」 を JSON で答えさせる
6. 検証 → 適用 → トゥームストーンを 1 件挿入
7. 実質削減が 0 以下ならロールバック。`forget` は失敗を報告し、`hybrid` だけが §6 の圧縮段階へ進む
```

縮約手段は **§6 の明示modeに一本化**する。`forget` の失敗を `compress` に自動置換せず、
両方を許可する場合だけ `hybrid` を選ぶ。

### 4.1 マニフェスト (モデルに見せる一覧)

トークンを食わないよう極力コンパクトに。 1 セグメント 1 行。

```
#1   user          1,240t  thin→1,180t  Discord Gateway の受信を WS 方式に切り替えたい。 まず現状の…
#2   tools         8,900t  thin→8,850t  grep×1, file_read×2  (src/discord/*)
#3   assistant       310t  thin→250t    Endpoint 方式は interaction-server.ts に実装されています。 …
#4   tools           180t  thin済       file_read×1  (src/agent/agent-loop.ts)
#5   assistant       180t  thin済       読み込みました。 次に gateway クライアントを実装します。
#6   tools         2,100t  thin→1,900t  file_write×1, bash×1  (src/discord/gateway.ts)
--- 以下は保護 (直近) ---
#7   user            90t   thin済       テストして
#8   tools         1,400t  thin→1,300t  bash×1
```

- 先頭の数値は **drop で減る量** (セグメントの total)、 `thin→Nt` は **thin で減る量** (`thinGain`)。
  total だけを見せるとモデルは thin 済みの大きなセグメントを選び、 削減 0 になる (§3.1)
- `thin済`: thin しても減らない (thin 済み・200 文字以下の短文)。 drop は選べる

digest の作り方:
- `user` / `assistant_text`: 本文の先頭 60 文字 (改行は空白化)
- `tool_batch`: `ツール名×回数` の集計 + 代表的な引数 (パス等) を 1 つ
  - パス (`file_path` / `path`) は **末尾優先**で 40 文字に収める (`…\src\game\campaign.js`)。
    先頭から切ると同一プロジェクト内のファイルが `C:\Users\…\src\g…` のように全部同じ表示になり、
    モデルが区別できないため (2026-10-15 acecomb セッションで実測)。 コマンド等は従来どおり先頭から切る

### 4.2 モデルへの指示

```
以下は現在の会話履歴の一覧です。 コンテキストが上限に近づいたため、
どれを残し、 どれを忘れるかを選んでください。

目標: 約 {targetTokens} トークン削減

判断基準:
- keep: ユーザーの指示・制約、 未解決の判断、 いま進行中の作業に必要な情報
- thin: 行動の記録は要るが結果の本文はもう要らないもの (再度ツールを実行すれば取り直せる)
- drop: 用済みの探索、 失敗して捨てた試行、 現在の作業と無関係な話題

原則: 迷ったら thin を選ぶ。 drop はユーザー指示を含まないと確信できるものだけ。

JSON のみを返してください:
{"thin": [2, 4], "drop": [], "reason": "巨大なソース読み込みの本文を落とした。 指示と判断は全て残した"}
```

`keep` を明示させず **thin / drop に挙げなかったものが keep** とする。
出力トークンを減らし、 かつ **「何も指定しない = 何も忘れない」 が安全側**に倒れるため。

**思考はオフで呼ぶ** (`ChatParams.disableThinking: true`)。 出力上限は `FORGET_MAX_TOKENS = 1500`。
思考モデルはプロンプトで「思考は最小限に」 と頼んでも守らず、 一覧を 1 件ずつ検討して
上限を思考だけで使い切り、 本文 (JSON) が空のまま終わる (2026-10-15 実測: Qwen3.8 Flash Next /
llama.cpp、 84 セグメントで `finish=length`・思考 3,228 字・本文 0 字が 2 回連続 → 忘却不成立)。
思考オフでは同じ一覧に対し約 8 秒・364 トークンで有効な JSON が返った。
上限を引き上げるだけでは、 一覧が長くなれば再び使い切るため根本対策にならない。

| provider | 送信内容 |
|----------|----------|
| `llamacpp` / `vllm` | `chat_template_kwargs: {enable_thinking: false}` |
| その他 | 送らない (未知フィールドで 400 を返し得る商用 API があるため)。 思考が続いて本文が空なら §4.5 の理由表示で分かる |

### 4.3 検証 (モデルの出力をそのまま信じない)

| 検証 | 違反時の扱い |
|------|-------------|
| 存在しない index | 無視 (警告ログ) |
| protected セグメントの指定 | 無視 (警告ログ) |
| `user` セグメントの `drop` | **`thin` に制限** — 忘却機能内の安全規則としてユーザーの言葉を完全消去させない |
| `thinGain` が 0 のセグメントの `thin` (格下げ後を含む) | 無視 (警告ログ)。 適用しても削減 0 でトゥームストーン分だけ増えるため |
| thin/drop が 0 件 | 忘却は不成立。履歴を保持し、`forget` は失敗を報告、`hybrid` のみ圧縮段階へ進む |
| JSON パース失敗 / 本文が空 | 同じ忘却経路で1回だけ再試行 → だめなら忘却不成立 (理由は §4.5) |

`user` の drop を格下げするのは、 「ユーザーが言ったこと」 が消えるのが
最も回復不能な損失だからである。 モデルが「雑談だから消してよい」 と判断しても、
後からユーザーが「さっき言ったよね」 と言う場面は普通に起きる。

### 4.4 トゥームストーン (忘却の記録)

適用後、 **最初に忘却したセグメントがあった位置**に system メッセージを 1 件残す。
履歴の先頭や末尾にまとめて置くのではなく、 元の時系列上の位置に置くことで
「この時点から先の情報が薄い」 という時間的な手がかりをモデルに残す。

```
[忘却の記録] 6 セグメント / 約 52,300 トークンを履歴から削除しました。
- 本文のみ削除 (行動の記録は残存): file_read×3, bash×2
- 完全削除: 探索目的の grep 結果 1 件
必要になった情報は再度ツールで取得してください。
```

`docs` の方針「silent な欠損は禁止・可視化せよ」 に従う。 **何が消えたか分からない
状態を作らない**ことが、 忘却機能が信頼されるための最低条件である。

トゥームストーンは `system_note` セグメントとして以後 **常に保護**される
(忘却の記録を忘却してしまうと辻褄が合わなくなる)。

複数回忘却が起きた場合、 直前のトゥームストーンに **追記統合**する
(トゥームストーンが履歴中に散乱するのを防ぐ)。

### 4.5 不成立の理由を分けて見せる

忘却プランが作れなかったとき、 理由を 1 つの文言にまとめない。 原因ごとに打ち手が違うためである。
`ForgettingEngine.planWithReason()` が理由を返し、 `ForgetResult.reason`
(= `contextReduction=forget` のエラー文、 `/forget dry`) にそのまま載る。

| 理由 | 表示例 | 打ち手 |
|------|--------|--------|
| 本文が空 | `モデルの応答本文が空でした (finishReason=length, 出力 1500 トークン)。 出力上限 1500 トークンを思考だけで使い切った可能性があります` | provider が思考オフ (§4.2) に対応しているか確認 |
| JSON が読めない | `モデルの応答を JSON として読めませんでした: <先頭 80 字>` | モデルの指示追従を確認 |
| 呼び出し失敗 | `忘却選択の LLM 呼び出しに失敗しました: <例外>` | 接続・サーバ側を確認 |
| 選択 0 件 | `モデルが忘れる対象を 1 件も選びませんでした (無効な指定 N 件を除外: …)` | 保護範囲・digest を確認 |
| 対象なし | `忘却できるセグメントがありません (直近の作業とノートはすべて保護対象)` | 圧縮 (`hybrid`) を検討 |

以前は `(JSON パース失敗 / 選択 0 件 / 対象なし)` の固定文言で、 詳細な警告は stderr にしか出ないため
後から原因を特定できなかった (silent な欠損の禁止に反する)。

## 5. 適用先: MessageHistory

新メソッドを 1 つ足す。

```ts
/**
 * 忘却の結果でメッセージ列を置き換える。
 * tool_calls / tool_result のペア整合を検証し、 壊れていれば例外を投げて
 * 呼び出し側にロールバックさせる (壊れた履歴を送ると provider が 400 を返すため)。
 */
replaceMessages(next: Message[]): void
```

呼び出し側 (`ForgettingEngine`) は適用前に `getRawMessages()` の控えを取り、
`replaceMessages` が投げたら控えに戻す。 **忘却の失敗で会話が壊れることはない**。

## 6. 縮約手段の選択 (`contextReduction`)

`config.context.reduction` を新設する。

| 値 | 動作 |
|----|------|
| `"compress"` | 従来通り常に圧縮 |
| `"forget"` | 常に忘却。 忘却が **適用できなかったとき (パース失敗・対象なし・ロールバック) だけ** 圧縮に倒す。 適用できたなら削減が足りなくても圧縮しない |
| `"hybrid"` (**既定**) | 上記に加えて、 **適用できても削減が目標の 60% 未満なら続けて圧縮**する |

2 つの mode の差はこの 1 点だけである。 `forget` は「要約による劣化を絶対に避けたい」
user 向けで、 削減不足はそのターンでは許容する (次ターンで再度忘却が走る)。
`hybrid` は確実にあふれを解消することを優先する。

既定を `hybrid` にする理由:

- 忘却だけでは足りない状況 (会話そのものが長い) が必ず存在する。 そのとき
  「忘却したが結局あふれる」 では機能として役に立たない
- 逆に圧縮だけだと §1.2 の劣化が毎回起きる
- 2 段構えなら **最悪でも従来と同じ**になる (= 後退しない)

なお `hybrid` は既定値の変更にあたるため、 初回起動時に `/context` で
現在の設定が確認できるようにし、 `/forget mode compress` で従来動作に戻せるようにする。

### 6.1 目標削減量

```
targetTokens = 現在の推定トークン - contextWindow * max(0.05, threshold - 0.15)
```

`max(0.05, …)` でクランプするのは、 threshold が 0.15 以下に設定された場合に
目標が発散して「全部忘却しろ」 になるのを防ぐため。

閾値の 15 ポイント下まで落とす。 閾値ちょうどを狙うと、 次のターンで即座に
再び閾値を超えて忘却が毎ターン走る (= LLM 呼び出しが毎ターン増える) ため、
**余裕を持って落とす**。

## 7. 圧縮と忘却の使い分け (F3 への橋渡し)

| 状況 | 向いている手段 | 理由 |
|------|--------------|------|
| ツール結果で膨らんだ | **忘却 (thin)** | 会話の筋を無劣化で保てる |
| 会話そのものが長い (設計議論が延々) | **圧縮** | 捨てられる本文が無い。 要約するしかない |
| タスクが完了して次に移る | **Clear + 引き継ぎ** | 前タスクの詳細は一切不要 |
| これから難所に入る | **事前に圧縮** | 山場で余裕を確保しておく |

この選択を **タイミングも含めて自動化する**のが後続の
`docs/context-strategy.md` (F3) の役割。 本設計では **手段を用意する**ところまで。

## 8. CLI

| コマンド | 動作 |
|----------|------|
| `/forget` | 今すぐ忘却を実行 (対話確認なし。 結果サマリを表示) |
| `/forget dry` | 忘却プランだけ出して適用しない (何が消えるか事前確認) |
| `/forget mode [compress\|forget\|hybrid]` | 縮約手段の切替 (引数なしで現在値表示) |
| `/forget status` | 現在の mode / 直近の忘却実績 |

`/compact` (圧縮) は現状のまま残す。 対になるコマンドとして `/forget` を置く。

`/forget dry` を用意するのは、 **最初にユーザーが不安を感じる機能**だからである。
「何が消えるのか」 を適用前に見られる経路が無いと、 怖くて使えない。

## 10. リスク

| リスク | 対策 |
|--------|------|
| モデルが必要な情報を忘却してしまう | (a) `user` の drop は thin に格下げ、 (b) 直近は保護、 (c) トゥームストーンで消したことを明示 → モデルが「読み直す」 判断を取れる |
| 忘却で履歴が壊れて provider が 400 を返す | セグメント単位なのでペアが分断されない。 さらに `replaceMessages` で検証 + 失敗時ロールバック |
| 忘却の LLM 呼び出し自体が遅い | マニフェストは 1 セグメント 1 行のみ (数百トークン)。 圧縮の 4〜5 回呼び出しより **速い**のが通常 |
| 思考モデルが出力上限を思考で使い切り、 本文が空になる | 忘却選択は思考オフで呼ぶ (§4.2)。 それでも空なら理由に `finishReason=length` を出す (§4.5) |
| 小さいモデル (T3) が JSON を返せない | 同じ忘却経路で1回再試行し、だめなら履歴保持で失敗。圧縮も許可する場合は最初から `hybrid` を明示する |
| 毎ターン忘却が走って遅くなる | 目標を閾値の 15 ポイント下に置く (§6.1)。 加えて最短間隔 (直前の忘却から 3 ターン) を設ける |
| **情報だけ失って削減量がゼロになる** | 小さいセグメントを thin してもトゥームストーン (数十トークン) の方が大きく、 実質削減が負になり得る。 適用後に実測し、 **削減が 0 以下ならロールバック**して `applied: false` を返す。 これが無いと最悪ケースで純粋に後退する |

## 11. 将来の拡張余地

- **忘却の取り消し**: 忘却前のスナップショットを 1 世代だけ保持し `/forget undo`
- **再取得の自動化**: トゥームストーンが指すツール呼び出しを、 モデルが必要としたとき
  自動で再実行する (今は「必要なら読み直して」 と伝えるだけ)
- **忘却ポリシーの学習**: どのセグメントを忘却した後に読み直しが発生したかを記録し、
  「読み直しが多い種類は忘却しない」 を統計で決める
- **セカンドLLM への委譲**: 忘却の選択はメインの思考を止めるので、 安いモデルに任せる
  (F1 の named slot が入ったので `forget` slot を割り当てれば実現できる)
