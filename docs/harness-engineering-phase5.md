# ハーネスエンジニアリング Phase 5: Claude Code 比較で見える本質的弱点と段階的改善計画

> **実装状況**: 未着手 (2026-04-26 起案)。最終的に全項目対応する予定。
> **位置づけ**: Phase 1-4 (`docs/harness-engineering.md`) の続編。前回はローカル27Bを動かすための"床上げ"。今回は **モデル性能に依存しない本質設計** に踏み込む。

---

## 0. 出発点: モデル性能を言い訳にしてはいけない

Phase 1-4 までは「Qwen 27B クラスのローカルLLMでもエージェントとして動かす」という前提だった。
Phase 5 の出発点は、**クラウドLLM (Kimi-K2.6) を実際に走らせたログ**で、**Phase 1-4 で改善したはずの同種の失敗パターンが依然として観測された**こと。

仮説:
- Claude Code は Claude 1.x 世代から十分役立つエージェントだった。Claude 4.x で性能は上がったが、エージェントとしての「動く / 動かない」の境界は、ハーネス設計が引いている
- lllmAgents が Kimi-K2.6 でなおコケる箇所は、**モデル性能ではなく、ハーネスがモデルを助け切れていない箇所**
- 「賢いモデルなら通るから問題ない」と判断してきた箇所こそ、設計の欠落

つまり Phase 5 のテーマは:
> **「賢いモデルでも引っかかる」=「ハーネスの責務」と認める。**

## 1. 評価対象とした失敗群 (評価者視点)

`~/.localllm/logs/sessions/` の Kimi-K2.6 走行ログから抽出。

| # | 失敗パターン | 観察 (証拠) | 影響 |
|---|---|---|---|
| F1 | 壁ドンループ (file_read) | 同一パスへの `File not found` × 7 + glob × 9 + sandbox_info × 8 | 1タスクで28回の無駄ツール呼び出し、~3-4分浪費 |
| F2 | 丸投げ連鎖 (second_llm_agent) | 18ターン中 21回 委任、同一ファイルに細切れ修正指示 | ターン数+20%、API コスト増、コンテキスト分散 |
| F3 | glob 試行錯誤 | pattern を 3-4回変えて探索 (`*.txt`→`*.html`→`**/*`) | 試行錯誤に1-2ターン浪費 |
| F4 | plan_mode 蒸発 | 最初の2ターン計画立案 → 後続で参照されず | 30-40 秒の純レイテンシ |
| F5 | write 後検証ゼロ | file_write/edit 後に状態確認なし、silent failure 可能性 | 信頼性低下 |
| F6 | 沈黙ターン | 思考だけで実行が進まないターン | コンテキスト圧迫 |
| F7 | ツール引数の誤解 | glob pattern 構文・拡張子省略の混乱 | 試行錯誤の温床 |

これらは「賢いモデルなら通り抜けたかもしれない」が、Claude Code では **発生する前にハーネス側で潰されている** タイプの失敗。

## 2. Claude Code が組み込んでいる本質パターン (設計者視点)

Claude Code (このアシスタント自身) の動作を内省して言語化する。
lllmAgents と一対一の比較に使う。

| パターン | 中身 | lllmAgents 現状 |
|---|---|---|
| **P1. 自助情報の標準同梱** | エラーは「失敗の事実」だけでなく「次に何を試せば抜けられるか」を含む。例: `string_to_replace not found` → 直近の Read で取得した内容 / 似た文字列の候補 / Write 推奨を返す | file-edit のみ実装済 (Phase 2)。他のツールは無情報 |
| **P2. 読まずに書かない契約** | Edit ツールは「同じセッションで Read 済み」を前提とした契約。違反すると最初から拒否する | 契約なし。Read せずに Edit/Write も通る |
| **P3. 同じ間違いを2度させない** | 連続失敗 N 回でハーネスが介入。失敗パターンを次のプロンプトに自動反映 | file-edit のみ実装済。他は無し |
| **P4. 観察可能性 (副次情報の標準同梱)** | Write 結果には bytes / 行数 / 構文チェック結果。Read 結果には「ファイルが切り詰められたか」「全体何行か」 | 部分実装。エラー時のみで、成功時は文字数程度 |
| **P5. 委任の閾値設計** | サブエージェント / Task は「コンテキスト保護」「並列性」「専門性」 の3条件のいずれかが満たされる時のみ。それ以外はインライン処理 | 閾値なし。モデルの一存。「セカンドLLMに頼っていい」とだけ書いてある |
| **P6. エスカレーション ladder** | 試行 → 失敗 → 状況再収集 → 別アプローチ → ユーザー確認、の階段が明示的に存在する | 階段の段が無く、同じ階で足踏みしやすい |
| **P7. 計画と実行の分離は重い案件のみ** | plan_mode 相当は「複雑度が閾値を超えた時だけ」。単純タスクで強制しない | 「とりあえず計画を立てよう」が起動しがち |
| **P8. ツールの利用目的を明示** | description に「いつ使うか」「使うべきでない時」「典型的な誤用」が含まれる | 機能の説明はあるが、誤用パターンや非推奨条件が薄い |
| **P9. ハーネス → モデル へ"気づき"を渡す** | 「直前のターンで X が起きました」を平文で挿入する仕組み | コンテキスト圧縮や autorun 表示はあるが、行動誘導目的の挿入は薄い |

**lllmAgents は P1, P3 を file-edit に限り実装。それ以外は未着手か断片的。**
これが「Phase 1-4 の成果が局所最適に留まっている」状態の正体。

## 3. 課題ごとの3視点深掘り

各課題を **観察 (評価者) → あるべき姿 (設計者) → 実装弱点 (製造者) → 段階的対応** の構造で書く。

### 課題A: 失敗フィードバックが「無情報」 (P1, P3 の汎化)

- **観察**: F1 の壁ドンループ。`file_read` のエラーは `File not found: path` のみで、ファイル名のタイポか拡張子違いか権限の問題かをモデルが切り分けるための情報がない
- **あるべき姿** (設計者): エラーは「失敗の事実 + 次の最善手の候補」を返す契約。例: `File not found: foo.txt` で同ディレクトリに `foo.html` があれば併記、無ければ親ディレクトリの軽量 `ls` を併記
- **実装弱点** (製造者): `src/tools/definitions/file-read.ts` がエラーを `throw new Error("File not found")` で済ませている。ファイル探索ロジックは glob ツールに分離されており、ハーネスから自動補完されない
- **段階的対応**:
  - **Phase 5-A1 (短期)**: file-read エラー時、stem 一致の他拡張子 + 親ディレクトリ ls (上位5件) を併記
  - **Phase 5-A2 (中期)**: 全ツールに `selfHelpHints()` を生やし、エラーカテゴリごとに「次の手」を返す共通インターフェース化
  - **Phase 5-A3 (長期)**: ツール非依存のエラー分類器をハーネスに置き、連続パターン (同ファイル N 回失敗) でハーネス側から自動探索 (find + grep) を実行して結果を tool_result にプリペンド

### 課題B: 委任の閾値設計がない (P5 の欠落)

- **観察**: F2。second_llm_agent が 18ターンで 21回起動。修正ごとに細切れ委任 → コンテキストが分散し、メイン側でどこまで何が達成されているか追跡不能に
- **あるべき姿** (設計者): 委任は3条件のいずれかが必要 — (1) コンテキスト保護 (大量ファイルを読ませる) / (2) 並列性 (複数調査) / (3) 専門性 (別モデルの強み)。条件不在ならインラインで処理。一度委任したら「成果物の完成」までは同じ委任内で完結させる
- **実装弱点** (製造者): `src/agent/system-prompt.ts` には「セカンドLLMが使える」事実は書かれているが、**いつ呼ぶ / 呼ばない / 連続呼びの禁忌** が明文化されていない。`second_llm_agent` ツール側にも閾値ガードがない
- **段階的対応**:
  - **Phase 5-B1**: system-prompt.ts に「委任の3条件」と「同タスクで連続委任が3回を超える時は集約せよ」の戦略節を追加
  - **Phase 5-B2**: agent-loop.ts に `delegationGuard.consecutiveSameTarget(N)` を導入。3回目以降は警告を tool_result に挿入し「修正リストを集約して1回で渡せ」と促す
  - **Phase 5-B3**: 委任の意思決定を可視化。`second_llm_agent` 呼び出し前に「3条件のどれを満たすか」を引数として要求し、満たしていなければハーネスが拒否

### 課題C: write/edit 後の観察可能性 (P4 の欠落)

- **観察**: F5。file_write 成功 = `File written: path` のみ。サイズ・行数・構文チェック結果がメインに返らない。委任先で書かれた成果物の検証手段がメインに無い
- **あるべき姿** (設計者): ツール結果は **副次情報を標準同梱**。メインがそれを読んで「次に何を確認すべきか」を判断できる
- **実装弱点** (製造者): file-write は構文チェックを Phase 3 で実装済 (JS/JSON のみ)。ただし返り値に統一フォーマットがなく、他言語は無視。file-edit / bash / web_fetch は副次情報がほぼ無い
- **段階的対応**:
  - **Phase 5-C1**: file-write/edit の成功時返り値を `{ path, bytes, lines, syntaxOk?, mtime, head?, tail? }` のように構造化。重要ファイル (拡張子 hint) は head/tail を併記
  - **Phase 5-C2**: bash の成功時に `exitCode, stdoutBytes, stderrBytes, durationMs` を併記
  - **Phase 5-C3**: web_fetch / browser_screenshot 等にも一貫した観察情報を追加

### 課題D: plan_mode の発動条件 (P7 の欠落)

- **観察**: F4。単純タスクでも「計画を立てます」から始まり、計画が後続で参照されない
- **あるべき姿** (設計者): 計画は「複雑度の高い案件」のためのもの。条件: (a) 影響ファイル数 ≥ 3 / (b) 複数言語混在 / (c) 既存仕様との整合性確認が必要 / (d) ユーザーが明示的に依頼。それ以外は計画スキップ
- **実装弱点** (製造者): system-prompt.ts と `enter_plan_mode` ツールの description が「複雑タスクの開始時に推奨」と曖昧
- **段階的対応**:
  - **Phase 5-D1**: system-prompt の plan_mode 節を「以下のいずれかを満たす時のみ起動」に書き換える。具体的閾値を提示
  - **Phase 5-D2**: `enter_plan_mode` ツールの description に "When NOT to use" 節を追加
  - **Phase 5-D3**: ハーネスが plan_mode 起動後に **計画の最終ステップで TaskWrite を強制**。捨てられない計画にする

### 課題E: glob のヒント不足 (P1 の特殊化)

- **観察**: F3, F7。pattern を `*.txt` → `*.html` → `**/*` と試行錯誤
- **あるべき姿** (設計者): hit 0 件の時、検索した親ディレクトリの一覧 (上位 N 件) を併記。pattern の typo 候補もサジェスト
- **実装弱点** (製造者): glob.ts の hit 0 時のレスポンスが「マッチなし」のみ
- **段階的対応**:
  - **Phase 5-E1**: hit 0 時に親ディレクトリの軽量 ls を併記。description に pattern の例 (`**/*.ts`, `src/**/test*.ts`) を 3-4 個追加
  - **Phase 5-E2**: 拡張子省略エラー (`*.txt` だが実態は `*.html`) を検出して suggestion を返す

### 課題F: 沈黙ターンと思考の冗長性 (Phase 4 で部分対応済の延長)

- **観察**: F6。Phase 4 で「テキストのみ応答」検出を入れたが、**短い思考 + 短いツール呼び出し** の組み合わせで「実質沈黙」が発生する
- **あるべき姿** (設計者): 進捗の有無を「ツール出力のバイト変化」「ファイルの mtime 変化」「TaskWrite のステータス遷移」で機械的に測る
- **段階的対応**:
  - **Phase 5-F1**: agent-loop.ts に `progressTracker` を導入。N ターン進捗ゼロを検出したら system insertion で「現状を整理して別アプローチを取れ」と促す
  - **Phase 5-F2**: 「思考だけ」検出を文字数閾値ではなく「ツール呼び出しに寄与しない思考」に判定基準を変える

### 課題G: ツール定義の利用目的明示 (P8 の欠落)

- **観察**: F7 + 全般的に。ツール description が機能列挙で、「いつ使う / いつ使わない / 典型的な誤用」が欠けている
- **あるべき姿** (設計者): description は最低限 ① 機能 ② 使うべき場面 ③ 使うべきでない場面 (近接ツールとの使い分け) ④ よくある誤用 の4要素
- **段階的対応**:
  - **Phase 5-G1**: 全ツールの description を上記4要素テンプレートで書き直す
  - **Phase 5-G2**: 近接ツール (file_read vs bash cat / glob vs bash find / file_edit vs file_write) の使い分け表を system-prompt に1個だけ置く

### 課題H: Read → Write の契約 (P2 の欠落)

- **観察**: file_edit 失敗の主因は「Read していない or 古い Read 結果に基づいた edit」。これはモデル能力でなく契約の欠落
- **あるべき姿** (設計者): file_edit は同セッション内の file_read 履歴 (またはほぼ等価な観察) を前提条件とし、満たさなければ拒否する。Claude Code 自体がそうなっている
- **実装弱点** (製造者): tool-executor 側に「依存関係」の概念がない
- **段階的対応**:
  - **Phase 5-H1**: agent-loop.ts に `recentReads: Map<path, mtime>` を持ち、file_edit 時に該当パスの Read が直近 N ターン以内に行われたかを検査。なければ「先に file_read を呼んでください」を返して拒否
  - **Phase 5-H2**: bash の編集系コマンド (`sed -i`, `>`, `>>`) も同等に扱うかを別途検討

## 5. 評価指標 (評価者視点)

リグレッション防止のため、**改善前後で機械的に測定できる指標**を定義する。
評価ログ (`~/.localllm/logs/sessions/*.jsonl`) からの自動集計を `scripts/eval-jsonl.js` (新規) で実装する想定。

| 指標 | 定義 | 目標 |
|---|---|---|
| 平均ツール呼び出し / ターン | 全ターン中のツール呼び出し総数 / 総ターン数 | 1.5 → 1.2 |
| 同一パス連続失敗率 | 同一ファイルパスへの連続エラー数 / 全エラー数 | 25% → 5% |
| 委任連続回数の中央値 | 同タスク内の連続 second_llm_agent 呼び出し | 4 → 2 |
| 進捗ゼロターン率 | ツール結果のバイト変化 = 0 のターン / 総ターン数 | 計測未実施 → 5% 以下 |
| plan_mode 起動率 | plan_mode 起動セッション / 総セッション数 | 80% → 30% |
| 平均タスク完了ターン数 | 同種タスクでの完了までのターン数 | ベースライン記録 → -25% |

評価フローは `docs/evaluation-loop.md` の枠組みを再利用する。

## 6. 失敗パターンの分類学 (今後の議論用語彙)

ハーネス改善議論を共通語で進めるための名前付け。

- **壁ドンループ (Wall-Hit Loop)**: 同じエラーに何度も突き当たる。 ⇒ P1, P3 で防ぐ
- **丸投げ連鎖 (Delegation Cascade)**: 委任 → 委任 → 委任。 ⇒ P5 で防ぐ
- **沈黙ターン (Silent Turn)**: 思考のみで進捗ゼロ。 ⇒ P9, F1 で防ぐ
- **計画蒸発 (Plan Evaporation)**: 計画を立てて参照されない。 ⇒ P7 で防ぐ
- **silent failure**: 失敗が外に伝わらない。 ⇒ P4 で防ぐ
- **盲目編集 (Blind Edit)**: 読まずに書く。 ⇒ P2 で防ぐ
