# 制作を履歴だけに依存させない

長い制作では、開発記録に次を更新する。頻繁なユーザー確認ではなく、まとまった実装の境界で行う。

```text
目標と現在のユーザー方針:
対象project/scene、保持する元資産:
実装済み（実ファイル・参照）:
未実装（次の具体的編集）:
確認済み（時点・状態・証拠path）:
未検証（実装不足と混ぜない）:
直近の失敗、原因、変更した一点、再確認結果:
現在のPlay/dirty/timeScale、未保存変更:
次に読むファイルと行う作業:
```

履歴整理が失敗したら、元履歴を捨てて成功扱いにしない。レート制限なら直ちに停止する。それ以外はエラーのfinish reason、出力打ち切り、JSON形状を区別する。アプリが復旧情報を返している場合はそれを使う。

再開時は記録を読み、ファイル・sceneを再取得して差分を確認する。過去の要約が「完成」と言っていても未実装なら制作を続ける。途中生成のsceneやコンポーネントを毎回新規追加して重複させない。

`/clear`などが必要なら、対象会話の履歴/ToDo/Goalが消えることと、保存済み制作ファイルが残ることを区別して説明する。保存や引き継ぎを確認せず履歴削除を指示しない。モデル・接続設定の切替はユーザーの選択を保持する。

## 再発時にどこを直すか

- 間違った判断やコードの組み立て方 → このスキル/対象projectの制作記録へ具体的な診断方法を残す。
- 内部の並列送信、レート制限の握り潰し、要約結果の破棄、schema/保存pathの扱い → アプリの不具合。スキルの注意書きだけで解決済みにしない。
- ユーザーが求めていないComputer Use改善・モデル変更・他サービス移行 → 勝手に制作へ混ぜない。
