# Product Quality Cycle

指定された観点を軸に、証拠に基づくレビューから検証済みの改善までを一周させる。観点の例は信頼性、セキュリティ、UX、自律性、可観測性、性能、リリース品質、最近追加した機能。

## 0. サイクル境界を固定する

1. 観点、対象範囲、完了条件を一文で定義する。指定が曖昧なら「商品レベル」を正しさ・安全性・運用性・UX・配布可能性として扱う。
2. リポジトリ指示、設計書、作業ツリー、ブランチ、最近の履歴を確認する。ユーザーの未コミット変更を分離し、触らない。
3. commit・pushは、明示依頼、リポジトリルール、またはユーザーの継続的な許可がある場合に行う。リポジトリが区切りごとのpushを既定としている場合は、個別依頼がなくても検証済みの変更だけをcommit・pushする。タグは明示依頼時だけとし、before タグは変更前の HEAD、after タグは検証済み commit を指すようにする。
4. 変更前に build・lint・test のベースラインを取り、製品不具合と環境起因の失敗を分ける。
5. Windows で UTF-8 の設計書・スキルを PowerShell から読む場合は `Get-Content -Raw -Encoding UTF8` を使う。文字化けの兆候があれば内容を解釈せず、UTF-8を明示して再読込する。

## 0.5. ユーザーとの通信と承認を集約する

1. 読み取り、ローカル検証、依頼範囲内の通常作業について会話上の確認を挟まない。判断に必要な情報はまずリポジトリから調べ、合理的な仮定で進める。
2. ユーザーまたはリポジトリルールが区切りごとのcommit・pushを許可済みなら、個別依頼を待たず、同じタスクの訂正commitにもその許可を適用する。stage・commit・push・CI開始を可能な範囲で一括し、同じ操作について会話上の再確認を重ねない。実行環境が要求する承認は、狭い対象の関連操作をまとめて一度で求める。
3. tool呼出しや変化のないCI pollごとに進捗報告しない。原因特定、実装・検証の区切り、新しい失敗、最終成功など、ユーザーの判断に影響する状態変化だけを報告する。長時間作業の定期報告も、直近の変化を集約した一件にする。
4. ユーザーからサイクル運用の再利用可能な欠陥を指摘され、永続化を求められた場合、「次回気をつける」で終えない。完了前に適用先の`AGENTS.md`、本スキル、テスト、または自動化へ反映し、保存先を引き渡しで示す。

## 1. レビューする

最低でも次の証拠を突き合わせる。

- 設計: `docs/` の期待、制約、未実装、古い記述
- 実装: 境界条件、例外、非同期処理、状態同期、秘密情報、配布時のパス
- テスト: 重要分岐、OS差、実環境・TTY・配布物の不足、回帰検出力
- 履歴: 指定日以降または直近の機能を commit 単位で追い、影響範囲を確認
- 実行ログ: 失敗頻度、長時間化、反復、コスト、容量、機密情報、ユーザー入力と内部注入の区別
- 配布物・CI: ソース上の資産が実際の package / exe / installer に入るか

ログではまず件数・期間・容量・エラー署名などの集計値を見る。プロンプト、応答、秘密情報は既定で転載せず、原文が不可欠な場合だけユーザーの許可を得る。巨大 JSONL は可能ならストリーム処理し、分析器そのものの誤集計も疑う。

## 2. 優先順位と改善設計を決める

発見事項を次で分類し、レビュー記録へ残す。

- P0: データ損失、重大な安全問題、主要機能が利用不能
- P1: 誤動作、課金・観測漏れ、停止・ハング、本番導入を妨げる問題
- P2: 保守性、性能、テスト・文書不足など短期改善
- P3: 微調整、将来改善

再現できる誤動作は「バグ」と明記し、証拠、原因、影響、修正方針、回帰テストを紐づける。実装単位は高リスクかつ検証可能な集合に分けてよいが、それは停止理由ではない。設計変更があれば先に `docs/` へ反映する。

## 3. 実装する

1. バグは可能なら失敗する回帰テストで固定する。
2. 原因に最小限の変更を加え、関連するインストーラー・配布スクリプト・文書も同時に直す。
3. 各まとまりごとに対象テストと型・静的検査を実行し、失敗したら原因を再確認する。
4. スコープ外のユーザー変更を stage、整形、削除しない。

## 4. 評価する

変更に比例して次を実行する。

1. 追加した回帰テストと関連テスト
2. 全 unit test、lint / typecheck、build
3. E2E、実 OS / TTY、配布物の smoke test（影響した場合）
4. ログ指標の再集計、または修正前後の再現比較
5. pushを依頼されている場合は、pushした最新SHAのCIを全依存job終了まで確認する。失敗・必須jobのskipは新しい発見事項としてサイクルを再開し、ローカル成功や一つ前のgreen runで完了扱いしない。
6. OS、ファイル時刻、列挙順、TTYなどに依存する失敗は、順序と時刻を決定的にしたうえで対象テストを反復し、flakeが消えた証拠を残す。

成功数だけでなく skip、既知失敗、未検証領域も記録する。テストが緑でも、実環境の証拠がなければ「実環境検証済み」とは扱わない。

## 5. 記録して引き渡す

レビュー記録には次を含める。

1. 観点、対象、日付、基準 commit / tag
2. ベースラインと利用した証拠
3. 重要度順の発見事項（バグを識別可能にする）
4. 今回の改善設計と実装内容
5. 修正前後の評価結果
6. 全発見事項の終端状態（修正済み、誤検出・重複、範囲外、blocked、ユーザー受容）
7. commit、before / after tag、push 先（依頼された場合）

push 前に stage 対象と diff を確認する。after タグは全検証後の commit に付け、branch と両タグを push してリモート上の参照を確認する。

CI成功後に記録だけのcommitを追加すると、そのcommitが新しい完了候補になる。記録は可能なら修正commitへ含める。後から記録commitをpushした場合も、その最新SHAのCIを監視せずに完了報告してはならない。

## 6. 終了判定と継続

サイクル番号は実装・評価のチェックポイントであって、引き渡し条件ではない。「次サイクル候補」「今回は選外」と記録しただけで終了してはならない。

1. 1サイクルで完了条件に届かなければ、完了とは報告しない。残課題、残った理由、優先度、次サイクルの実施範囲と品質ゲートをユーザーへ明示し、そのまま次サイクルを実行する提案をする。
2. 同じ依頼の観点・完了条件に含まれる実行可能な課題が残るなら、ユーザーが中止・範囲変更を指示しない限り、提案した次の実装・評価サイクルを同じタスク内で開始する。
3. 「商品レベル」が範囲なら、レビューで発見した P0/P1 は同じ依頼の範囲内として扱う。修正済み、誤検出・重複と実証済み、外部条件または追加権限により blocked、ユーザーが明示的に受容、のいずれかになるまで完了にしない。
4. P2/P3 も完了条件に必要なら継続して直す。残す場合は、当初範囲外である根拠と品質ゲートを妨げない証拠、または具体的 blocker を示す。「工数が大きい」「次回が望ましい」だけでは範囲外・blocked の根拠にならない。
5. 新しい課題の発見が止まり、品質ゲートを通り、未解決項目が上記の終端状態だけになってから引き渡す。
6. pushが範囲に含まれる場合、最新のpush済みSHAで必須CI jobがすべて成功するまで終了しない。CI失敗後は以前の完了判定を取り消し、同じサイクルの発見事項として閉じる。

## 完了条件

- [ ] 指定観点と最近の機能を含むレビュー証拠がある
- [ ] 発見したバグがレビュー記録に残っている
- [ ] 全発見事項が修正済み・誤検出/重複・範囲外・blocked・ユーザー受容のいずれかになっている
- [ ] 商品レベル指定で未解決の P0/P1 が残っていない
- [ ] 修正に回帰テストまたは同等の再現評価がある
- [ ] 対象テストと全体品質ゲートの結果を記録した
- [ ] 設計・実装・配布物の整合を確認した
- [ ] ユーザー所有の変更を混入させていない
- [ ] 明示依頼または継続的な許可があるcommit・pushを完了し、タグは明示依頼時だけ作成した
- [ ] pushした場合、最新SHAの必須CI jobがすべて成功した
- [ ] 再利用可能な運用上の指摘について、永続化を求められた場合はルール・スキル・テスト・自動化へ反映した
