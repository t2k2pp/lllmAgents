# 新規マルチファイルプロジェクト作成

「ゼロから立ち上げる」 専用のスキル。 **既存リポジトリへの変更は対象外** — それは `/dev-workflow` か通常編集で行う。

## このスキルが効くケース

- 「Snake ゲームを作って」「ToDo アプリを作って」 → ゼロから複数ファイル一気作成
- 「Anthropic SDK のサンプル集を作って」 → samples/ 配下に新規プロジェクトディレクトリ
- 「テンプレ的な HTML+CSS+JS を出して」 → output/ 配下

## このスキルが効かないケース (使わない)

- 1 ファイルの新規追加 → 普通に `file_write`
- 既存プロジェクトに新ファイルを 1-2 個足す → `/dev-workflow`
- 既存ファイルの変更 → 普通に `file_edit`
- リファクタ・機能廃止 → `/refactoring`

## 出力先のルール (CLAUDE.md 準拠)

- ユーザー検証物 (生成成果物) は **`sandbox/` 配下に絶対パス** で出力
- リポジトリルート直下に作らない
- 相対パス禁止

具体的に:

| 種類 | 出力先 |
|------|--------|
| ゲーム・サンプル Web アプリ | `sandbox/<project-name>/` (リポジトリ外なら user 指定の絶対パス) |
| ドキュメント・設計書 | `docs/` (ただしリポジトリ内の機能追加に伴う設計書だけ) |
| user の単発依頼物 (PPTX/XLSX 等) | `sandbox/` |

## 手順

### Step 1: 要件確認 (簡潔に)

- 何を作るか (名前・目的)
- 技術スタック (HTML+JS / Node / Python / etc.)
- 出力先の **絶対パス** (未指定なら `sandbox/<project-name>/` を提案)
- 「ガッツリ」 か 「最低限」 か

不明な要素が 2 つ以上あれば `ask_user`。 1 つだけなら推定して進めて user に推定根拠を伝える。

### Step 2: ファイル一覧と依存関係を設計

`todo_write` で:

```
1. <絶対パス>/constants.js — 定数
2. <絶対パス>/utils.js — 共通関数
3. <絶対パス>/core.js — コアロジック (1, 2 に依存)
4. <絶対パス>/index.html — エントリポイント (3 に依存)
```

**依存される側 → 依存する側** の順で並べる。

### Step 3: 依存順に生成 (並列化可能なら並列)

1. **依存される側から `file_write`** (constants → utils → core → entry)
2. **同レイヤで独立しているファイルは 1 レスポンスで並列 `file_write`**
3. 各 `file_write` 後、 次のファイルを書く前に **前のファイルの export 名・関数シグネチャを確認** (memory 内に保持)
4. **完全に動作する状態で書く** — `// TODO` / 未実装関数 / 空の throw を残さない
5. **配列インデックスの浮動小数点** ・**NaN 混入** に注意 (`game-development` で観測された罠 — `Math.floor()` で必ずラップ)

### Step 4: 整合性検証

全ファイル作成後:

```
1. エントリポイント (index.html / main.js / etc.) を file_read
   - <script src> / import パスが全て正しいか
2. コアファイルを file_read
   - 他ファイルの関数・クラス名が正確か (typo していないか)
3. 問題があれば file_edit ではなく file_write で全体書き直し (確実)
```

JS/TS なら `node --check <file>` を bash で叩いて構文エラーゼロを確認。 Python なら `python -c "import ast; ast.parse(open('<file>').read())"`。

### Step 5: 完了報告

- 出力先の絶対パス
- 作成したファイル一覧
- 使い方 (例: 「ブラウザで index.html を開く」「`python main.py` で実行」)

## 落とし穴

| 罠 | 回避策 |
|----|--------|
| テキストで計画を述べるだけで `file_write` を呼ばない | 設計したら即座に書き出す。 user に確認するのは Step 1 だけ |
| 大量ファイル時の依存順序ミス | todo_write で順序を可視化、 順番通り実行 |
| 同じ操作の連続失敗 | 2 回失敗したら別アプローチに切り替え (file_edit → file_write 全書き直し 等) |
| 巨大単一ファイル | ロジックがある程度大きいなら分割。 1 ファイル 500 行を超えたら分割検討 |

## ゲーム特化の追加ルール

ゲームを作る場合は **`/game-development`** スキルの規約 (NaN 混入禁止、 `Math.floor()` 必須、 ゲームループ完全実装、 README 同梱) も併せて適用する。

## 完了条件

- [ ] 全ファイルが `sandbox/` 配下の絶対パスに作成済み
- [ ] エントリポイントから全ファイルへの参照が解決する
- [ ] 構文エラーゼロ (`node --check` 等で確認)
- [ ] user に使い方が伝わっている
