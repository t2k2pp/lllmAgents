# 第 2 章：インフラ設計と選定

## はじめに

生成 AI システムのインフラ設計は、パフォーマンス、コスト、セキュリティに直結します。本章では、クラウド vs オンプレミスの比較、分散環境の構築、スケーラビリティの考慮を解説します。

---

## 2-1 クラウド vs オンプレミスの比較

### クラウド環境

#### 主要クラウドプロバイダー

**AWS**:
```
- SageMaker（ML 専用）
- EC2（汎用）
- Lambda（サーバーレス）
```

**Azure**:
```
- Azure ML
- Virtual Machines
- Azure Functions
```

**Google Cloud**:
```
- Vertex AI
- Compute Engine
- Cloud Functions
```

#### クラウドのメリット

**1. スケーラビリティ**
```
- 自動スケーリングが可能
- 需要に応じたリソース調整
- 地理的な分散が容易
```

**2. コスト効率**
```
- 初期投資が不要
- 従量課金
- 未利用リソースの削減
```

**3. 管理の容易さ**
```
- 保守・更新がプロバイダーが担当
- セキュリティパッチの自動適用
- バックアップの自動化
```

#### クラウドのデメリット

**1. コストの変動**
```
- 利用量増加でコスト増
- 予測が困難
- 隠れたコストの可能性
```

**2. ベンダーロックイン**
```
- プロバイダー依存
- 移行コスト
- 価格交渉の不利
```

**3. データ sovereignty**
```
- データの所在地制限
- コンプライアンスの複雑化
- 法的制約
```

### オンプレミス環境

#### 構成要素

```
┌─────────────────────────────┐
│      サーバーラック             │
│  ┌─────────┐ ┌─────────┐   │
│  │ GPU サーバー│ │GPU サーバー│   │
│  └─────────┘ └─────────┘   │
│  ┌─────────┐ ┌─────────┐   │
│  │ ストレージ │ │ネットワーク│   │
│  └─────────┘ └─────────┘   │
└─────────────────────────────┘
```

#### オンプレミスのメリット

**1. 完全な制御**
```
- ハードウェアの完全な制御
- ネットワークの完全な制御
- セキュリティの完全な制御
```

**2. データプライバシー**
```
- データが社内に残る
- 外部への送信なし
- コンプライアンス容易
```

**3. 予測可能なコスト**
```
- 初期投資後の固定費
- 利用量に関係しない
- 長期コストが低い（高利用時）
```

#### オンプレミスのデメリット

**1. 初期投資**
```
- ハードウェア購入コスト
- データセンター構築コスト
- 設置・設定コスト
```

**2. 管理コスト**
```
- 専任チームが必要
- 保守・更新の負担
- 障害対応の負担
```

**3. スケーラビリティの制限**
```
- 物理的な制限
- 拡張に時間がかかる
- 過剰投資のリスク
```

### 比較サマリー

| 項目 | クラウド | オンプレミス |
|------|---------|-----------|
| 初期コスト | 低 | 高 |
| 運用コスト | 変動 | 固定 |
| スケーラビリティ | 高 | 低 |
| 制御性 | 中 | 高 |
| データプライバシー | 中 | 高 |
| 保守負担 | 低 | 高 |

## 2-2 分散環境の構築

### 分散環境の必要性

大規模な生成 AI システムでは、単一サーバーでは対応できない場合があります。

#### 分散が必要なケース

**1. 高トラフィック**
```
- 多数の同時ユーザー
- 大量のリクエスト
- 地理的な分散
```

**2. 高可用性**
```
- 24/7 稼働必須
- 障害許容
- リカバリーの迅速化
```

**3. 大規模モデル**
```
- メモリ制限
- 計算リソース不足
- 分散推論が必要
```

### 分散アーキテクチャ

#### 1. 水平スケーリング

```
┌─────┐     ┌─────┐     ┌─────┐
│ LB  │────▶│ Node│     │ Node│
└─────┘     │  1  │     │  2  │
            └─────┘     └─────┘
              │           │
              └───────────┘
                共有ストレージ
```

**特徴**:
- ノードを追加してスケール
- 負荷分散器（LB）を配置
- ステートレス設計

**実装例（Kubernetes）**:
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: llm-service
spec:
  replicas: 3
  selector:
    matchLabels:
      app: llm-service
  template:
    spec:
      containers:
      - name: llm
        image: llm-service:latest
        resources:
          limits:
            nvidia.com/gpu: 1
```

#### 2. 垂直スケーリング

```
┌─────────────────────┐
│    大規模サーバー       │
│  ┌───────────────┐   │
│  │   多数 GPU      │   │
│  │   大メモリ       │   │
│  └───────────────┘   │
└─────────────────────┘
```

**特徴**:
- 単一サーバーの強化
- GPU、メモリの増設
- 管理が容易

#### 3. ハイブリッド

```
┌─────────────┐     ┌─────────────┐
│ クラウド環境    │     │ オンプレミス    │
│ ┌─────────┐ │     │ ┌─────────┐ │
│ │ 汎用タスク │ │     │ 機密タスク │ │
│ └─────────┘ │     │ └─────────┘ │
└─────────────┘     └─────────────┘
```

**特徴**:
- 両者のメリットを享受
- 柔軟なリソース配分
- コスト最適化

### 負荷分散の戦略

#### ラウンドロビン

```
Request 1 → Node 1
Request 2 → Node 2
Request 3 → Node 3
Request 4 → Node 1
```

#### 最少接続

```
- 接続数が少ないノードに割り当て
- 負荷の偏りを防止
```

#### 地理的分散

```
- ユーザーの所在地に近いノードへ
- 遅延の最小化
```

## 2-3 スケーラビリティの考慮

### スケーラビリティの種類

#### 1. 読み取りスケーラビリティ

```
┌─────┐     ┌─────────┐     ┌─────┐
│User │────▶│  キャッシュ  │────▶│ LLM  │
│     │     │ (Redis)   │     │ API │
└─────┘     └─────────┘     └─────┘
```

**戦略**:
- レスポンスのキャッシュ
- CDN の利用
- 読み取りレプリカ

#### 2. 書き込みスケーラビリティ

```
┌─────┐     ┌─────┐     ┌─────┐
│User │────▶│ キュー  │────▶│Worker│
│     │     │     │     │     │
└─────┘     └─────┘     └─────┘
                │
                ▼
            ┌─────┐
            │Worker│
            └─────┘
```

**戦略**:
- メッセージキュー
- 非同期処理
- バッチ処理

### パフォーマンス指標

#### 1. 遅延（Latency）

**目標値**:
```
- 初回トークン：500ms 以内
- トークン生成：50ms/トークン 以内
```

**改善策**:
```
- モデルの最適化
- ネットワークの最適化
- キャッシュの活用
```

#### 2. スループット

**目標値**:
```
- リクエスト/秒：100+
- 同時接続：1000+
```

**改善策**:
```
- ホライゾンタルスケーリング
- リソースの最適化
- 負荷分散
```

#### 3. 可用性

**目標値**:
```
- 可用性：99.9% 以上
- RTO（回復目標時間）：1 時間以内
- RPO（回復目標ポイント）：5 分以内
```

**改善策**:
```
- マルチアベイラビリティーゾーン
- 自動フェイルオーバー
- 定期的なバックアップ
```

### スケーリングの自動化

#### 自動スケーリングの要件

**指標ベース**:
```yaml
# Kubernetes HPA 例
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: llm-service
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70
```

**タイムベース**:
```
- 業務時間の事前スケールアップ
- 夜間スケールダウン
- 休日設定
```

## 2-4 ハイブリッド環境の設計

### ハイブリッド環境のメリット

**1. コスト最適化**
```
- 定常負荷：オンプレミス
- 変動負荷：クラウド
```

**2. セキュリティ**
```
- 機密データ：オンプレミス
- 一般データ：クラウド
```

**3. 柔軟性**
```
- 需要に応じたリソース配分
- 災害復旧の容易化
```

### 設計パターン

#### パターン 1: ブレイクガラス

```
正常時：
┌─────────────┐
│ オンプレミス    │
│  全トラフィック  │
└─────────────┘

ピーク時：
┌─────────────┐   ┌─────────────┐
│ オンプレミス    │   │ クラウド      │
│  基本トラフィック │   │  追加トラフィック│
└─────────────┘   └─────────────┘
```

#### パターン 2: データ分離

```
機密データ：
┌─────────────┐
│ オンプレミス    │
│ 機密処理        │
└─────────────┘

一般データ：
┌─────────────┐
│ クラウド      │
│ 一般処理        │
└─────────────┘
```

#### パターン 3: 地理的分散

```
日本：
┌─────────────┐
│ オンプレミス    │
│ 日本ユーザー    │
└─────────────┘

海外：
┌─────────────┐
│ クラウド      │
│ 海外ユーザー    │
└─────────────┘
```

### 実装のポイント

#### 1. 一貫性の確保

**構成管理**:
```
- Infrastructure as Code
- 一貫した設定
- バージョン管理
```

**監視**:
```
- 統一した監視ツール
- 一貫したログフォーマット
- 統合ダッシュボード
```

#### 2. ネットワーク設計

**接続**:
```
- 専用線（Direct Connect）
- VPN
- 公開インターネット
```

**セキュリティ**:
```
- ファイアウォール
- 暗号化
- アクセス制御
```

---

## 本章のまとめ

1. クラウドとオンプレミスにはそれぞれメリット・デメリットがある
2. 分散環境は高トラフィック・高可用性に必要
3. スケーラビリティは設計段階から考慮する
4. ハイブリッド環境で柔軟性とコスト最適化を実現
